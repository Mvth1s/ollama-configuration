# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this project does

A set of Bash scripts (under `scripts/linux/`) that install and configure a local Ollama stack (LLM inference + Open WebUI) on Linux, plus a separate native PowerShell implementation (`scripts/windows/setup.ps1` + `scripts/windows/lib/common.ps1`) for Windows, plus two optional Tauri apps: `gui/` (one-off install) and `launcher/` (day-to-day: open Open WebUI, manage models). The four numbered Bash scripts can be run individually or chained via `setup.sh`; `setup.ps1` is the single Windows entry point (see [Windows script](#windows-script-setupps1--libcommonps1) below). This `scripts/linux/` + `scripts/windows/` split is Phase 1 of the SelfLlama restructure (mechanical reorganization only, no behavior change) — see the note at the top of [Architecture](#architecture) below. The two script implementations are independent: the Windows script does not wrap or require WSL, and is not a literal port — it is adapted to Windows/PowerShell primitives (CIM, winget, scheduled tasks) with the same overall shape (logging, shared state, RAM/GPU detection, model tiers) kept in sync by hand. `gui/` (see [Desktop GUI](#desktop-gui-gui) below) is purely an orchestration layer over `setup.sh`/`setup.ps1`: it never reimplements detection or tier logic itself. `launcher/` (see [SelfLlama Launcher](#selfllama-launcher-launcher) below) is a separate app that never touches the install scripts at all, talking directly to Ollama's and Open WebUI's own local APIs instead.

## Requirements

- Linux (Arch, Debian/Ubuntu, Fedora, openSUSE — other distros require manual GPU driver installation): bash ≥ 4.0 (associative arrays used throughout), `curl`, `sudo` privileges for package installation and systemd configuration
- Windows: PowerShell 5.1+, `winget` recommended (used to install Ollama/Python unattended; falls back to downloading the official installer otherwise)
- Desktop GUI (`gui/`, `launcher/`, both optional): Rust/`cargo`; on Linux, WebKitGTK dev packages (`libwebkit2gtk-4.1-dev`, `libgtk-3-dev`, `libsoup-3.0-dev` on Debian/Ubuntu). No Node.js/npm needed — both frontends are plain HTML/JS with no build step.

## Running the scripts

```bash
# Full install (auto-detects GPU and RAM)
./scripts/linux/setup.sh

# Force a specific model tier
./scripts/linux/setup.sh --tier=M

# Skip model download or web UI
./scripts/linux/setup.sh --skip-models
./scripts/linux/setup.sh --skip-webui

# Run individual steps
./scripts/linux/01-install-ollama.sh
./scripts/linux/02-configure-gpu.sh
./scripts/linux/03-pull-models.sh --tier=S
./scripts/linux/04-install-webui.sh

# Disable the interactive dialog/whiptail menus
./scripts/linux/setup.sh --no-tui

# Allow/restrict Open WebUI access from other devices on the network, any time
./scripts/linux/toggle-webui-lan.sh on|off|status
```

```powershell
# Windows: full install, auto-detection
.\scripts\windows\setup.ps1

# Force a specific model tier
.\scripts\windows\setup.ps1 -Tier M

# Skip model download or web UI
.\scripts\windows\setup.ps1 -SkipModels
.\scripts\windows\setup.ps1 -SkipWebui

# Allow/restrict Open WebUI access from other devices on the network, any time
.\scripts\windows\toggle-webui-lan.ps1 on|off|status
```

There are no build steps for the Bash/PowerShell side — these are operational scripts, not a compiled project. There is, however, a `tests/` bats suite (see [Tests](#tests) below). Bash scripts are linted with [ShellCheck](https://www.shellcheck.net/) (`.github/workflows/lint.yml`, called by `ci.yml` on every push/PR — see [Tests](#tests) below for the full CI pipeline shape; run locally with `(cd scripts/linux && shellcheck -x *.sh lib/*.sh)` — from within `scripts/linux/` itself, not the repo root, since ShellCheck `-x` resolves each script's bare `source lib/common.sh` relative to its own working directory rather than the checked file's directory); `scripts/windows/setup.ps1`/`scripts/windows/lib/common.ps1`/`scripts/windows/toggle-webui-lan.ps1` are linted the same way with [PSScriptAnalyzer](https://github.com/PowerShell/PSScriptAnalyzer) in the same workflow (`Invoke-ScriptAnalyzer -Path scripts/windows/setup.ps1, scripts/windows/lib/common.ps1, scripts/windows/toggle-webui-lan.ps1`, one file per call since `-Path` only accepts a single string; PowerShell's `$PSScriptRoot`-relative dot-sourcing means this one has no equivalent working-directory sensitivity). The job fails on *any* remaining `Warning`- or `Error`-severity finding, except for a fixed `-ExcludeRule` list of deliberate design choices documented inline in `lint.yml` (`PSAvoidGlobalVars`, `PSAvoidUsingWriteHost`, `PSUseApprovedVerbs`, `PSReviewUnusedParameter`, `PSUseShouldProcessForStateChangingFunctions`) — this baseline has been audited down to zero unexcluded findings, so nothing here is unaudited lint debt.

## Tests

`tests/*.bats` ([bats](https://github.com/bats-core/bats-core)) exercises `scripts/linux/lib/common.sh` (distro/RAM detection, the `state.env` round trip) and the branching logic in `01-install-ollama.sh`/`02-configure-gpu.sh`/`03-pull-models.sh`/`toggle-webui-lan.sh` (all under `scripts/linux/`; GPU vendor priority, model tier selection, the CPU-only downgrade rule, LAN toggle, and the `--detect-only`/`--model-<usage>=` additions used by `gui/`'s wizard — see [Detection-only mode](#detection-only-mode-and-non-interactive-model-overrides-for-the-gui-wizard)). Run with `bats tests/*.bats` from the repo root (no install needed beyond `bats` itself, e.g. `apt install bats` or `git clone` [bats-core](https://github.com/bats-core/bats-core) and call `bin/bats` directly).

Every test runs the real script (not a reimplementation of its logic) against a throwaway `$HOME` and a stub `PATH` set up by `tests/test_helper.bash` (its `REPO_ROOT` points at the repo root; individual `.bats` files invoke scripts under `$REPO_ROOT/scripts/linux/`): `sudo` and `systemctl` are always stubbed (so nothing ever touches the real system, regardless of what's actually installed on the machine running the suite), and each test stubs whichever of `lspci`/`rocminfo`/`nvidia-smi`/`free`/`ollama`/`curl` it needs to control. `sudo`'s stub only drains stdin for `sudo tee` (piped into from `write_amd_override`) — draining it unconditionally would also eat the stdin meant for `02-configure-gpu.sh`'s Nvidia-driver `read -r -p` prompt further down the same script. `lib/common.sh`'s `detect_distro` reads `$OS_RELEASE_FILE` (defaulting to `/etc/os-release`) rather than the hardcoded path, and `02-configure-gpu.sh`'s `find_rocminfo` reads `$ROCM_OPT_DIR` (defaulting to `/opt`) rather than a hardcoded `/opt/rocm*` — purely so tests can point either at a throwaway file/directory instead of the real one. Three of `configure_gpu_vendor.bats`'s `find_rocminfo` tests go a step further than the usual `stub_cmd`: since simply not stubbing `rocminfo` isn't enough to prove the `/opt/rocm` fallback actually triggers on a machine that happens to have a real `rocminfo` reachable elsewhere on the ambient `PATH` this sandbox inherits (true of any real ROCm dev machine, including the one that originally reported this bug), those tests build a minimal `PATH` (`$STUB_BIN` plus symlinks to only the specific external tools the script chain needs, resolved from whatever the real ones are) that excludes `rocminfo` entirely, rather than relying on it being coincidentally absent.

This suite caught two real `set -euo pipefail` bugs in `02-configure-gpu.sh` on the first run: `write_amd_override` piping a command group into `sudo tee` where the group's last command could be a false `[ -n "$override" ] &&` test (making the whole pipeline — and the script — exit non-zero even though nothing was wrong), and `configure_nvidia` ending on a false `if [ "$install_confirmed" -eq 1 ]; then ... fi` with no trailing command when the user declined the driver-install prompt. Both are instances of the same class of bug: a conditional whose false branch has no following statement, as the *last* thing executed in a function/script under `set -e`, propagates its test's failure as the function's own exit status. Watch for this pattern (prefer `if`/`fi` with an explicit trailing `return 0`/`true` over a bare `cond && cmd` as the last statement) when adding new branches to any of these scripts.

`gui/src-tauri` and `launcher/launcher-core` each have a `#[cfg(test)] mod tests` block (`cargo test` from within the crate directory). `gui/`: `find_marker_upwards` (the walk-up-from-executable logic behind `find_repo_root`), and `extract_detect_json`/the `DetectResultRaw`→`DetectResult` merge (the `__DETECT__`-line parsing behind `detect_system`, exercised with fixed JSON fixtures rather than a real script run). `launcher-core` (see [SelfLlama Launcher](#selfllama-launcher-launcher) below for why this logic lives in its own tauri-free crate rather than `launcher/src-tauri` directly): `to_model_info` (Ollama `/api/tags` response mapping, including the empty-string default when `details` is absent), `parse_systemctl_is_active` (empty-output → `"unknown"` fallback), `build_lan_url` (IPv4 vs. bracketed-IPv6 formatting), and `parse_webui_lan_status`/`format_webui_env` (the `webui.env` read/write logic behind `webui_lan_status`/`set_webui_lan`). As with `to_model_info`, every test targets a pure function extracted out of its `#[tauri::command]` — none of them spawn a real process, hit the network, or need a live systemd/Ollama session.

`launcher/src-tauri`'s `mod tests` also has one exception to that rule: `pull_list_and_delete_round_trip_against_live_ollama`, marked `#[ignore]`, exercises `pull_model`/`list_models`/`delete_model` against a **real**, locally running Ollama daemon and its actual HTTP API (pulls the small `all-minilm` model, checks it shows up via `list_models`, deletes it, checks it's gone) — the one gap fixture-based tests can't cover, since they'd only ever confirm the code parses JSON the way we assume Ollama returns it, not that it still does. `pull_model` itself needs a Tauri `AppHandle` to emit progress events (only available inside a running app, not a plain `#[test]`), so its HTTP/NDJSON logic is split into a plain `pull_model_inner(model: &str, on_progress: impl FnMut(PullProgress))`, called by both the real `#[tauri::command]` (with a closure that does `app.emit(...)`) and this test (with a closure that just flips a bool). `#[ignore]` keeps it out of `cargo test`/CI's `test.yml` by default (it needs network access and a live Ollama); `.github/workflows/launcher-ollama-integration.yml` runs it explicitly via `cargo test -- --ignored`, `workflow_dispatch`-only (not on every push/PR) since it downloads a real model every run.

### E2E/UI tests (`gui/e2e-tests`, `launcher/e2e-tests`)

Before this, `gui/dist`/`launcher/dist` had no end-to-end coverage at all — only pure functions extracted out of their `#[tauri::command]`s were unit-tested (previous paragraphs above). Each app now also has a small [WebdriverIO](https://webdriver.io/) suite (`gui/e2e-tests/`, `launcher/e2e-tests/`, each its own `package.json`/`package-lock.json` — devDependency-only tooling that never ships with either app, same category as the root `package.json`'s release tooling, not a break from the "zero npm dependency" rule for the shipped frontends themselves) driving the **real, compiled app window** through [`tauri-driver`](https://crates.io/crates/tauri-driver) and `WebKitWebDriver` (the Linux WebKitGTK WebDriver binary, from the `webkit2gtk-driver` package — a different package from the `libwebkit2gtk-4.1-dev` already installed for compiling), headless under `xvfb-run`. Setup mirrors [Tauri's own WebdriverIO guide](https://v2.tauri.app/develop/tests/webdriver/example/webdriverio/) almost verbatim: `wdio.conf.js`'s `onPrepare` runs a plain `cargo build` (no `tauri-cli`/bundling involved, per `gui/README.md`/`launcher/README.md`'s dev workflow) so the debug binary (`../src-tauri/target/debug/selfllama-gui` / `selfllama-launcher`) exists, `beforeSession` spawns `tauri-driver` from `~/.cargo/bin`, and `afterSession`/shutdown handlers kill it again.

Both suites were run for real against the actual built app windows (not just written blind): `gui/e2e-tests/test/specs/wizard.e2e.js` checks step 1's synchronously-rendered title/subtitle (`main.js`'s `HEADERS`, independent of `detect_system`'s async result, so it stays fast and non-flaky), the 4-item stepper with only step 1 active, and that only `#step-1` is visible; `launcher/e2e-tests/test/specs/launcher.e2e.js` checks the static `<h1>` heading (deliberately not the async service-status/LAN-toggle state, which would be racy without an explicit wait) and that the service/LAN cards exist. Doing this surfaced one real bug in the test itself before it ever reached CI: the launcher's `<h1>` is a child of `<main>`, not `<body>` directly, so an initial `body > h1` selector failed against the real DOM — fixed to `main > h1`.

`.github/workflows/e2e.yml` runs two jobs, `e2e-linux` (`ubuntu-latest`) and `e2e-windows` (`windows-latest`), each a matrix over `gui`/`launcher`. `e2e-linux` is the original, proven job: installs `webkit2gtk-driver`+`xvfb` alongside the existing WebKitGTK dev packages, `cargo install tauri-driver --locked`, `npm install` in the app's `e2e-tests/`, then `xvfb-run --auto-servernum npm test`.

`e2e-windows` was added in a later session with no Windows machine/VM available to test it, only Tauri's own documented WebDriver-on-Windows conventions to go on (WebKitWebDriver has no Windows equivalent; `tauri-driver` instead needs a `msedgedriver.exe` matching the runner's installed Edge version, passed via `--native-driver`, since there's no PATH auto-discovery for it the way there is for `WebKitWebDriver` on Linux). The job reads the installed Edge's `ProductVersion` from `Program Files (x86)\Microsoft\Edge\Application\msedge.exe` (falling back to `Program Files` if not found there), downloads the matching `edgedriver_win64.zip`, and exports its path as `TAURI_DRIVER_NATIVE_DRIVER` via `$env:GITHUB_ENV` for the `npm test` step to read. `gui/e2e-tests/wdio.conf.js`/`launcher/e2e-tests/wdio.conf.js` both gained an `isWindows` branch: the app binary gets a `.exe` suffix, and `beforeSession` passes `--native-driver $TAURI_DRIVER_NATIVE_DRIVER` to `tauri-driver.exe` when that env var is set. No `xvfb-run` equivalent is used - `msedgedriver` drives a real (non-headless) window on the runner's own desktop session, unlike `WebKitWebDriver`'s headless-under-Xvfb setup.

**First real run (PR #65) confirmed the prediction that the msedgedriver-matching step would be the most likely failure point - but not for the guessed reason.** `windows-latest`'s Edge version was read correctly (`Program Files (x86)` path was right, no channel surprise: `150.0.4078.65`) - the real cause was that `msedgedriver.azureedge.net` (the download host originally used here) no longer resolves at all (`Invoke-WebRequest: No such host is known`). Microsoft has since moved Edge WebDriver downloads to `msedgedriver.microsoft.com` - confirmed with a real `curl -I` returning HTTP 200 and the matching `edgedriver_win64.zip` for that exact detected version. Fixed by switching the download URL; the `wdio.conf.js`/app side needed no change, as predicted. `setup.ps1`/the Windows side of `gui`/`launcher`'s *install* flow is still not exercised by these specs either way - this only extends the existing wizard/launcher-window smoke tests to run on Windows too, it doesn't add new Windows-specific specs. **Still not verified**: whether the rest of the job (actually launching the app under `msedgedriver` and running the specs) succeeds past this point - that only shows up on the next CI run after this fix.

`.github/workflows/test.yml` runs both the bats suite and `cargo test` for both apps. `.github/workflows/rust-ci.yml` separately runs `cargo clippy --all-targets --all-features -- -D warnings` and `cargo build --all-targets` for `gui/`/`launcher/` — previously these only ever got compiled at release time by `build-desktop.yml` after a version tag was already pushed, so a broken build was invisible until a release was underway. clippy runs with `-D warnings`: the `gui`/`launcher` baseline was confirmed clean (zero warnings) by PR #13's CI run, so this catches new warnings immediately instead of letting them accumulate as unaudited lint debt.

None of `lint.yml`/`test.yml`/`rust-ci.yml`/`e2e.yml`/`release.yml` trigger on their own anymore — each is `on: workflow_call` (plus `workflow_dispatch` for a standalone manual run) and is only ever invoked by `.github/workflows/ci.yml`, the single push/PR entry point. `ci.yml` calls `lint`+`test` first (the two fast jobs — ShellCheck/PSScriptAnalyzer/bats/`cargo test` all finish in well under the time a full Tauri build takes), then `rust-ci`+`e2e` with `needs: [lint, test]` so the two expensive jobs (a full `cargo build` twice over, and the WebDriver suite — the single most expensive job in the repo) never start if the cheap ones already failed. `ci.yml` also has `paths-ignore: ["**/*.md", "docs/**"]`, so a doc-only push/PR (this repo's own `CLAUDE.md`, `README.md`, the `gui`/`launcher` READMEs, `docs/`) skips the whole pipeline — a push mixing doc and code changes still runs everything, since the filter applies to the full push diff, not commit-by-commit. `.github/dependabot.yml` covers the two `cargo` manifests, the root `npm` one, and GitHub Actions versions, all on a weekly schedule.

## Architecture

Linux scripts live under `scripts/linux/` (numbered scripts, `lib/common.sh`, `setup.sh`, `toggle-webui-lan.sh`); the Windows implementation lives under `scripts/windows/` (`setup.ps1`, `lib/common.ps1`, `toggle-webui-lan.ps1`). This split (Phase 1 of the SelfLlama restructure) is purely mechanical — no logic changed, every script still `cd`s to its own directory and sources its sibling `lib/common.*` exactly as before. `application/core` (Phase 3 of the restructure — see its own section below) now exists alongside these, holding a pure-Rust port of part of their detection and install-planning logic; `application/src-tauri` (Phases 4/6 — see its own section below) holds `application::privileged`, the single-elevation-prompt install-phase mechanism built on top of `core::install`'s plans. As of Phase 7, `gui/src-tauri` is the first (and so far only) real consumer of both: `run_linux` now calls `application::privileged` directly instead of spawning `pkexec` three times itself — see [Desktop GUI](#desktop-gui-gui) below. `scripts/linux/01-install-ollama.sh`/`02-configure-gpu.sh`/`04-install-webui.sh --install-deps` remain unchanged and still work standalone; they are simply no longer what `gui/`'s privileged phase runs under the hood. Neither `application/core` nor `application/src-tauri` is a Tauri app of its own — `application/src-tauri` still has no `tauri` dependency, only a `[lib]`+`[[bin]]` pair reused by `gui/src-tauri` as a path dependency.

All scripts source `lib/common.sh` at startup, which provides:
- **Logging helpers**: `log_info`, `log_ok`, `log_warn`, `log_err`
- **Distro detection**: `detect_distro` sets `DISTRO_FAMILY` (arch / debian / fedora / opensuse / unknown) by reading `/etc/os-release` fields `ID` and `ID_LIKE`. Its already-set guard treats a cached `unknown` (e.g. from a stale `state.env`) as not set, so a machine that failed to detect once — a missing/unreadable `/etc/os-release` on that run — automatically retries on the next run instead of being stuck reporting `unknown` forever; any other cached value (a real distro family) is still trusted and skips re-detection.
- **Package installation**: `pkg_install <pkg>…` dispatches to the right package manager for the detected distro
- **Shared state**: `load_state` / `save_state VAR…` persist variables (GPU vendor, RAM, tier, distro) to `~/.config/selfllama/state.env` so later scripts can skip re-detection when chained together, but still work correctly when run standalone. `migrate_legacy_state_dir` (called once, at source time) moves an existing pre-rename `~/.config/ollama-stack/` wholesale to `~/.config/selfllama/` the first time any script runs after upgrading — a no-op once migrated, or on a fresh install; if both directories happen to exist already, the old one is left untouched rather than merged. `launcher/src-tauri`'s own `state_dir()` (Linux) and its embedded `set_webui_lan` PowerShell script (Windows) carry the identical migration, since the launcher can be opened without ever re-running `setup.sh`/`setup.ps1` after an upgrade.
- **TUI helpers**: `tui_available` detects a usable backend (`dialog`, else `whiptail`, else none), `tui_yesno` / `tui_menu` wrap the two; `detect_tui` treats `--no-tui` (sets `NO_TUI=1`) and a non-interactive stdin/stdout as "no backend" so scripted/chained calls never block on a prompt

To force full re-detection on the next run, delete `~/.config/selfllama/state.env`.

### Script responsibilities

| Script | Role |
|--------|------|
| `01-install-ollama.sh` | Installs Ollama via the official curl script; enables and waits up to 30 s for the systemd service |
| `02-configure-gpu.sh` | Detects GPU vendor via `lspci` PCI IDs (`10de`=Nvidia, `1002`/`1022`=AMD, `8086`=Intel — not commercial card names, which are unreliable), priority Nvidia > AMD > Intel for hybrid configs; installs drivers/Vulkan packages, writes a systemd drop-in (`/etc/systemd/system/ollama.service.d/override.conf`) for AMD Vulkan workarounds or Intel Vulkan; Nvidia uses CUDA with no override needed |
| `03-pull-models.sh` | Selects a model tier (XS/S/M/L) based on RAM and GPU presence, then pulls four models: texte, code, reflexion, embeddings |
| `04-install-webui.sh` | Installs Open WebUI via `pipx` (fallback: `pip`), creates a **user-level** systemd service (`~/.config/systemd/user/open-webui.service`) on port 8080, bound to `127.0.0.1` only by default |
| `toggle-webui-lan.sh` | Not part of the chain, run standalone at any time: flips Open WebUI between `127.0.0.1`-only and LAN-reachable (`0.0.0.0`) and restarts the service — see [Open WebUI LAN access toggle](#open-webui-lan-access-toggle) |

### AMD GPU handling

`02-configure-gpu.sh` uses `rocminfo` to read the real GFX code (e.g. `gfx1201`) rather than card names. The `AMD_GFX_OVERRIDE` associative array maps unsupported GFX codes to an `HSA_OVERRIDE_GFX_VERSION` value, enabling the Vulkan fallback for RDNA4 and future generations without maintaining a list of card names.

`rocminfo` isn't always on `PATH`: confirmed in production on an Arch/EndeavourOS machine with an AMD RDNA4 GPU, where the `rocminfo` package installs the binary under `/opt/rocm/bin` (or a version-suffixed `/opt/rocm-X.Y.Z/bin` on distros keeping multiple ROCm releases side by side) without ever adding it to `PATH`. `find_rocminfo()` checks `PATH` first (`command -v`, the only lookup this script used before this fix), then `$ROCM_OPT_DIR/rocm/bin/rocminfo`, then the first executable `$ROCM_OPT_DIR/rocm-*/bin/rocminfo` match, falling back to the pre-existing "chip not recognized" behavior (plain Vulkan, no HSA override) if none is found anywhere. `ROCM_OPT_DIR` defaults to `/opt` and is overridable — same testability pattern as `OS_RELEASE_FILE` (see [Tests](#tests) above) — so `tests/configure_gpu_vendor.bats` can point it at a throwaway directory instead of the real `/opt`. `application/core/src/detect/gpu.rs`'s `resolve_rocminfo_path` is a pure-function port of the same priority (`PATH` > plain `/opt/rocm/bin` > first versioned `/opt/rocm-*/bin` match), taking the pre-gathered lookup results as arguments rather than doing the filesystem/PATH checks itself, same convention as the rest of that crate — validated by fixtures only, **not** against real AMD RDNA4 hardware (none was available in the session that added it).

### Nvidia GPU handling

If `nvidia-smi` is not found, `02-configure-gpu.sh` **interactively prompts** the user before installing drivers, then exits asking for a reboot. Re-run after reboot to complete configuration.

### Intel GPU handling

There is no dedicated Ollama backend for Intel, so `02-configure-gpu.sh` enables the Vulkan backend (Mesa ANV driver) via the systemd drop-in, setting both `OLLAMA_VULKAN=1` and `OLLAMA_IGPU_ENABLE=1` (the latter is required for Ollama to actually consider integrated GPUs rather than only discrete ones). This is best effort — covers Xe/Iris iGPUs and Arc GPUs, and falls back to CPU silently if it doesn't activate.

**No iGPU-vs-Arc distinction, and this is deliberate, not an oversight**: `configure_intel()` applies `OLLAMA_VULKAN=1`+`OLLAMA_IGPU_ENABLE=1` uniformly to *any* `GPU_VENDOR=intel` match, integrated or discrete. A distinction was discussed during earlier planning — the idea being that Vulkan is more likely a net win on a discrete Arc card than on some weaker iGPUs, where plain CPU inference can sometimes be faster — but it has never been implemented or validated against real discrete Arc hardware in any session that has touched this script; it remains an untested hypothesis, not a confirmed behavior. Don't add an iGPU/Arc branch here (in `02-configure-gpu.sh` or in `application/core/src/detect/gpu.rs`) without testing on real Arc hardware first — unlike the `rocminfo` `PATH` issue above (a confirmed regression, now fixed), coding this distinction without validation would risk baking in a guess as if it were verified behavior.

### Open WebUI LAN access toggle

Open WebUI's `serve` command has no environment variable for its bind address, only a `--host` CLI flag (upstream default `0.0.0.0`) — confirmed by reading `open_webui`'s own `serve()` definition, since this is easy to get wrong silently. `04-install-webui.sh` therefore writes the desired host to its own small file, `~/.config/selfllama/webui.env` (`WEBUI_HOST=127.0.0.1` by default, only created if missing so re-running the installer never resets a later choice), and references it from the unit via `EnvironmentFile=`. The `ExecStart=` line reads `--host \${WEBUI_HOST}` with the `$` escaped in the heredoc so it reaches the unit file literally — systemd itself substitutes `${WEBUI_HOST}` from `EnvironmentFile=` into `ExecStart=` at service-start time (verified empirically with a throwaway unit; this is a systemd feature, unrelated to Open WebUI). `toggle-webui-lan.sh on|off|status` only rewrites `webui.env` and reloads/restarts the service — it never regenerates the unit file, so it works instantly without re-running the installer. `WEBUI_AUTH` is intentionally *not* touched by the toggle: enabling LAN access never silently enables auth, and both scripts print a warning explaining that when LAN access is turned on.

### Model tiers

Tiers are defined as associative arrays `MODEL_XS/S/M/L` in `03-pull-models.sh`. Auto-selection is RAM-based, with a forced downgrade to S on CPU-only machines:

| Tier | RAM | Text | Code | Reasoning | Embeddings |
|------|-----|------|------|-----------|------------|
| XS | ≤ 8 GB | llama3.2:3b | qwen2.5-coder:3b | deepseek-r1:1.5b | nomic-embed-text |
| S | ≤ 16 GB | llama3.1:8b | qwen2.5-coder:7b | deepseek-r1:7b | nomic-embed-text |
| M | ≤ 32 GB | gemma3:12b | devstral:24b | deepseek-r1:14b | nomic-embed-text |
| L | > 32 GB | gemma3:27b | qwen2.5-coder:32b | deepseek-r1:32b | nomic-embed-text |

The tier selection uses `declare -n` (bash nameref) to dynamically reference the right `MODEL_<TIER>` array.

### Interactive model selection (TUI)

`03-pull-models.sh` also defines `CAND_<TIER>_<usage>` arrays (e.g. `CAND_S_texte`), each holding 2-3 `"model|description"` candidates per tier/usage. When no `--tier=` was forced, `tui_available` is true, and the terminal is interactive, `select_models_tui` shows one `tui_menu` per usage and overwrites the tier's default with the user's pick via the `tier_models` nameref; a cancelled/failed menu keeps the tier default. This selection step is skipped entirely (default model kept) when `--tier=` is forced, `--no-tui` is passed, or no `dialog`/`whiptail` backend is available, so `setup.sh` and any scripted call remain fully unattended.

Similarly, `02-configure-gpu.sh`'s Nvidia driver install confirmation uses `tui_yesno` when a backend is available, falling back to the original `read -r -p` prompt otherwise.

### Detection-only mode and non-interactive model overrides (for the GUI wizard)

`02-configure-gpu.sh --detect-only` and `03-pull-models.sh --detect-only` are a second, machine-readable entry point alongside the interactive/scripted paths above, used by `gui/`'s installer wizard (see [Desktop GUI](#desktop-gui-gui) below). Each runs only its existing read-only detection functions (`detect_distro`, `detect_all_gpus`, the new `detect_cpu` in `lib/common.sh`, `detect_ram`, `compute_tier`) — never the driver-install or model-download logic — then prints one line prefixed `__DETECT__` followed by a JSON object, and exits 0 before doing anything else. `02-configure-gpu.sh`'s JSON carries `distro_pretty`/`gpu_vendor`/`gpu_name`/`cpu_model`/`cpu_threads`; `03-pull-models.sh`'s carries `ram_gb`/`tier`/`tier_models`/`candidates` (the same `MODEL_<TIER>`/`CAND_<TIER>_<usage>` data the TUI picker already uses, just serialized instead of shown in a `dialog` menu). A caller merges the two JSON objects itself. `lib/common.sh`'s `json_escape` (backslash/double-quote only) is the one shared piece of JSON-building logic; the rest is plain `printf`/array-to-JSON assembly local to each script.

`03-pull-models.sh` also accepts `--model-texte=`, `--model-code=`, `--model-reflexion=`, `--model-embeddings=` for the real (non-detect) run: applied right after `compute_tier`, they mutate `tier_models[$usage]` exactly the way `select_models_tui` already does from a `dialog`/`whiptail` menu, just sourced from CLI flags instead — this is how a caller with its own picker UI (rather than a TUI) applies the user's per-usage choice. Each override uses a full `if`/`fi` (never a bare `[ -n "$X" ] && tier_models[...]=...`), consistent with the `set -e` gotcha documented in [Tests](#tests) below.

`setup.ps1 -DetectOnly` is the Windows counterpart: calls `Get-RamGb`/`Get-GpuVendor`/`Get-CpuInfo` (new, in `lib/common.ps1`, same read-only shape as `Get-RamGb`)/`Get-ModelTier`, then prints one `__DETECT__`-prefixed line via `ConvertTo-Json` using the *same snake_case key names* as the Bash JSON (`distro_pretty`, `gpu_vendor`, ...) so a Rust caller can parse both platforms' output with one set of field names, and exits before `Install-OllamaWindows`. **Its JSON now includes a `candidates` field too** (`setup.ps1`'s own `$ModelCandidates` table, the Windows counterpart to `CAND_<TIER>_<usage>`, added after the Linux-only `application/core::install::tier` port made the underlying data easy to keep in sync by hand across all three places — see `core::install::tier`'s own doc comment). There is still no TUI/interactive picker on Windows itself (`Get-ModelTier`/`Install-Model` remain unattended, by design, same as always) — `$ModelCandidates` exists purely for `-DetectOnly` to report, so a caller with its own picker UI (the Tauri GUI wizard) can offer alternatives. **Not verified with a real PowerShell run in the session that added it** (no `pwsh` available in that session's sandbox): the JSON shape and `-Depth` value need confirming against a real Windows/PowerShell run before being trusted blindly.

`setup.ps1` also accepts `-ModelTexte`/`-ModelCode`/`-ModelReflexion`/`-ModelEmbeddings`, the CLI-only counterpart to `03-pull-models.sh`'s `--model-<usage>=`: `Set-ModelOverride` mutates `$ModelTiers[$Global:Tier][usage]` in place (hashtables are reference types in PowerShell, so this is visible to both `Install-Model` and the `-DetectOnly` JSON), called right after `Get-ModelTier` in both the `-DetectOnly` branch and the real run — same ordering as the Bash script, so an override passed alongside `-DetectOnly` is reflected in the reported `tier_models` too. These flags only ever mutate `$ModelTiers` (the resolved default), never `$ModelCandidates` (the fixed alternative list) — same relationship as `tier_models[$usage]=` vs. the `CAND_<TIER>_<usage>` arrays in `03-pull-models.sh`.

## Windows script (`setup.ps1` + `lib/common.ps1`)

A single-file orchestrator (`setup.ps1`) plus a shared library (`lib/common.ps1`), dot-sourced the same way `lib/common.sh` is on Linux — not split into four numbered scripts, since the roadmap that introduced it only called for these two files. `lib/common.ps1` provides:
- **Logging helpers**: `Log-Info`, `Log-Ok`, `Log-Warn`, `Log-Err` (`Write-Host` with `-ForegroundColor`, not raw ANSI codes, for PowerShell 5.1 console compatibility)
- **Shared state**: `Load-State` / `Save-State -VarNames …` persist globals (`RamGb`, `GpuVendor`, `GpuName`, `Tier`) to `%APPDATA%\selfllama\state.env`, using the same `VAR="value"` line format as Linux's `state.env` so both files stay easy to read side by side. `Migrate-LegacyStateDir` is the Windows counterpart to `lib/common.sh`'s `migrate_legacy_state_dir` — same one-time, no-op-after-the-first-run move of a pre-rename `%APPDATA%\ollama-stack\` to `%APPDATA%\selfllama\`
- **`Get-RamGb`**: RAM rounded up to the next GB via `Get-CimInstance Win32_ComputerSystem`
- **`Get-GpuVendor`**: reads `PNPDeviceID` from `Get-CimInstance Win32_VideoController`, matching the *same* PCI vendor IDs as `02-configure-gpu.sh` (`10DE`=Nvidia, `1002`/`1022`=AMD, `8086`=Intel), priority Nvidia > AMD > Intel
- **`Get-CpuInfo`**: CPU model name + logical thread count via `Get-CimInstance Win32_Processor`, display-only (no tier/config decision depends on it) — Windows counterpart to `detect_cpu` in `lib/common.sh`

`setup.ps1` itself:
- Defines `$ModelTiers` with the same tags as `MODEL_XS/S/M/L` in `03-pull-models.sh` — **kept in sync by hand**, update both when changing a model
- `Install-OllamaWindows`: installs via `winget` if available, else downloads and runs the official `OllamaSetup.exe` interactively; either way, verifies `ollama` is actually on `PATH` afterwards and errors out asking for a new terminal if not (a fresh PowerShell session is needed to pick up a PATH change made by the installer)
- `Set-GpuConfig`: **intentionally minimal**, unlike `02-configure-gpu.sh` — the official Windows installer already handles CUDA/ROCm natively, so this only logs the detected vendor and warns for AMD that the chip may be outside ROCm's officially supported list on Windows (no Vulkan-override equivalent is attempted)
- `Get-ModelTier` / `Install-Model`: same RAM thresholds and CPU-only downgrade-to-S rule as `03-pull-models.sh`'s `compute_tier`; no TUI/interactive model picker on Windows
- `Install-OpenWebUI`: installs via `pipx` (fallback `pip`), then registers a **per-user Scheduled Task** (`OpenWebUI`, `AtLogOn` trigger) instead of a systemd unit — Windows has no systemd — serving on the same port 8080; `OLLAMA_BASE_URL`/`WEBUI_AUTH` are persisted with `[Environment]::SetEnvironmentVariable(..., 'User')` since scheduled tasks inherit the user's persisted environment rather than accepting an `Environment=` block like systemd. Unlike `WEBUI_AUTH`, the bind address has no env-var equivalent on the Open WebUI side (only a `--host` CLI flag, same constraint as Linux — see [Open WebUI LAN access toggle](#open-webui-lan-access-toggle)), so `$Global:WebuiHost` (persisted like `Tier`/`GpuVendor` via `Save-State`, `127.0.0.1` by default) is baked directly into the scheduled task's `-Argument` string at registration time.
- `toggle-webui-lan.ps1`: the Windows counterpart to `toggle-webui-lan.sh`. Since there's no systemd-style `EnvironmentFile=` substitution to lean on, it rebuilds the scheduled task's action with `Set-ScheduledTask -Action` (reusing the already-registered `Execute` path) and restarts the task — no reinstall needed. Also never touches `WEBUI_AUTH`, same reasoning as the Linux script.
- `-DetectOnly`: see [Detection-only mode](#detection-only-mode-and-non-interactive-model-overrides-for-the-gui-wizard) above.

Does not reuse or wrap the Bash scripts, including under WSL — it is a separate, native Windows implementation, so GPU/RAM/tier logic must be updated in both places when it changes.

## Desktop GUI (`gui/`)

A [Tauri](https://tauri.app) app (Rust backend in `gui/src-tauri/`, vanilla HTML/CSS/JS frontend in `gui/dist/`, no npm dependency — `tauri.conf.json` sets `app.withGlobalTauri = true` so the frontend uses the injected `window.__TAURI__` global instead of importing `@tauri-apps/api`). See `gui/README.md` for build/run instructions and full detail. Key points:
- The numbered scripts (`01-install-ollama.sh` through `04-install-webui.sh`, `lib/common.sh`, now sourced from `scripts/linux/`) and `setup.ps1`/`lib/common.ps1` (now sourced from `scripts/windows/`) are bundled as Tauri resources (`tauri.conf.json`'s `bundle.resources`, both platforms' files included unconditionally in every package since a few KB of unused-on-that-OS scripts costs nothing that matters) and resolved at runtime via `find_scripts_dir()` (`app.path().resource_dir().join("scripts")`) in `src-tauri/src/main.rs`. This exists because a packaged install (`.deb`/`.rpm`/`.AppImage`/`.msi`/`.exe`, downloaded from GitHub Releases) has no repo checkout anywhere near it — a real user hit exactly this, `find_repo_root()` erroring "could not locate setup.sh in any parent directory of the running executable", since that older approach only ever worked for `cargo run`/`cargo build` from within a repo checkout (or a binary manually placed at the repo root, never an actual requirement anyone downloading a release build would know to do). `find_repo_root()`/`find_marker_upwards()` (walking up from the executable's directory) are kept as the fallback `find_scripts_dir()` uses when the resource directory doesn't have the scripts — i.e. still the dev-mode (`cargo run`) path, exercised by the existing unit tests.
  - **Known gap opened by the `scripts/linux/` + `scripts/windows/` split (SelfLlama restructure Phase 1)**: the *packaged* path above is unaffected — only `bundle.resources`' source side changed, its destination inside the bundle is still the flat `scripts/` layout `find_scripts_dir()` expects. But `find_repo_root()`'s dev-mode fallback still walks up looking for `setup.sh`/`setup.ps1` and, once found, treats that directory as the flat scripts directory — both assumptions this reorg just broke (the marker now lives at `scripts/linux/setup.sh` / `scripts/windows/setup.ps1`, not at the repo root next to the other numbered scripts). `cargo run`/`cargo build`-based dev testing of `gui/` will fail to locate the scripts until `find_repo_root()`/`find_marker_upwards()` are updated to account for the new layout; this was deliberately left untouched in Phase 1 (mechanical reorg only, no changes to `gui/`/`launcher/` code) and needs a decision before merging or before relying on `cargo run` for dev testing.
- The single `run_install` Tauri command spawns the platform script and streams stdout/stderr line-by-line back to the frontend as `install-log` events (plus a final `install-done`), via two reader threads per child process to avoid pipe-buffer deadlocks. Line-splitting is done by `stream_ansi_aware()`, not plain `BufRead::lines()` (which only splits on `\n`): `03-pull-models.sh`'s `ollama pull` renders its progress with ANSI cursor-control sequences (`ESC [ 1 G` to return to column 1, redrawing the same line) rather than ever printing `\n` mid-download — confirmed by capturing its raw piped output, which had only a handful of real newlines across an entire pull, all the percentage/spinner updates in between being `ESC [ 1 G` redraws. Plain `.lines()` would buffer an entire model download silently, appearing to the user as the GUI being stuck at 0% doing nothing (reported live by a user) even though the download was progressing normally. `stream_ansi_aware()` treats a bare `\r` and `ESC [ <n> G` as line boundaries too, so live progress streams to the frontend log pane the way it would render in a real terminal; other CSI sequences (cursor show/hide, erase-line, ...) are recognized and dropped rather than shown as literal escape codes.
- **Linux**: only `01-install-ollama.sh`/`02-configure-gpu.sh` (system-level: packages, systemd units) run through `pkexec`; `03-pull-models.sh`/`04-install-webui.sh` (per-user state: `pipx`, `~/.config/systemd/user/`) run unprivileged. Wrapping the whole `setup.sh` in `pkexec` would run everything as root and misplace that per-user state — this is why the GUI invokes the four scripts separately instead of calling `setup.sh`. The `pkexec` child is detached into its own session via `detach_from_tty` (`libc::setsid()` in a `pre_exec` hook) so it has no controlling terminal, otherwise `pkexec` silently falls back to a text password prompt on `/dev/tty` when no polkit agent is registered — leaking into whatever terminal launched the GUI instead of showing the graphical prompt or failing loudly.
  - **A third privileged step, `04-install-webui.sh --install-deps`, runs via `pkexec` right after `01`/`02`, before the unprivileged steps.** Found from a real user's report (`v1.1.3`): `04-install-webui.sh`'s own `pkg_install python3 python3-pip pipx` (see `lib/common.sh`'s `pkg_install`, always shells out to `sudo`) hung indefinitely when the GUI ran it as its supposedly-unprivileged webui step — `sudo`'s auth cache is entirely separate from `pkexec`'s, so authenticating for `01`/`02` doesn't cover it, and with `Stdio::null()` stdin and no controlling terminal, `sudo` can never get a password, so the whole process just blocks forever (confirmed via `ps`: the GUI process stayed alive in state `S`, not crashed, until manually killed). `--install-deps` runs only `pkg_install`'s idempotency-checked half (`install_webui_deps` in `04-install-webui.sh`, skipped entirely if `pipx` is already present) via `pkexec` like `01`/`02`; the main, still-unprivileged `04-install-webui.sh` run afterwards then finds `pipx` already there and never calls `sudo` itself. Gated on `!opts.skip_webui`, same as the main `webui` step. No equivalent issue on Windows: `setup.ps1` runs the whole install (privileged and unprivileged parts alike) under one `Start-Process -Verb RunAs`, so there's no separate unprivileged step for this class of bug to hide in.
- **Windows**: `setup.ps1` is invoked as a whole via `Start-Process -Verb RunAs`, since UAC elevation keeps the same user account (unlike `pkexec` switching to root), so there is no equivalent per-user-state problem there.
- The `open_webui_window` command opens (or focuses) a second window pointed directly at `http://127.0.0.1:8080` via `WebviewUrl::External`, reusing the same Tauri app rather than a separate webview technology; identical on Linux/Windows since it only uses Tauri's own window APIs. Always enabled — no "is Open WebUI up" check, a not-yet-running server just shows a connection error in that window.
- `gui/src-tauri/target/` and `gui/src-tauri/gen/schemas/` are gitignored (build artifacts); `gui/src-tauri/Cargo.lock` is committed intentionally (binary application, not a library).

### Installer wizard (`gui/dist/`) and `detect_system`

The frontend is a 4-step wizard (Détection → Modèles → Installation → Terminé), not a single flat form: `main.js` keeps a plain in-memory `state` object (current/max step, per-usage model choices, install step statuses) and re-renders targeted DOM sections on change — no framework, matching the rest of the repo's zero-npm-dependency frontends.
- **Détection**: on mount, calls the `detect_system` Tauri command (`DetectOptions { tier }` in, `DetectResult` out), which shells out to the `--detect-only`/`-DetectOnly` paths described [above](#detection-only-mode-and-non-interactive-model-overrides-for-the-gui-wizard) — unprivileged, no `pkexec`/`RunAs`, since detection alone needs no elevated rights. `detect_linux` runs `02-configure-gpu.sh --detect-only` then `03-pull-models.sh --detect-only` and merges their two `__DETECT__` JSON objects (via a `DetectResultRaw` deserialize struct matching the scripts' snake_case keys, converted to a `DetectResult` with `#[serde(rename_all = "camelCase")]` for the frontend, mirroring `ModelInfo`'s Rust→JS convention in `launcher/`); `detect_windows` calls `setup.ps1 -DetectOnly` directly (no `Start-Process -Verb RunAs`) and parses its single JSON line the same way. The frontend's row-by-row reveal on this screen is a purely cosmetic staggered animation over the *already-fetched real result* — not simulated/fake detection.
- **Modèles**: renders one card per usage from `DetectResult.tierModels`/`.candidates`; the "Changer" dropdown is hidden when `candidates` is empty for that usage. Populated on **both** platforms now (`gui/dist/main.js`'s dropdown logic was always generic, keyed only on `candidates.length` — it needed no change once `setup.ps1 -DetectOnly` started reporting real `$ModelCandidates` data). The user's picks are collected into `InstallOptions.models` (`Option<HashMap<usage, model>>`, no longer Linux-only) and become `--model-<usage>=` flags on the real `03-pull-models.sh` invocation in `run_linux`, or `-ModelTexte`/`-ModelCode`/`-ModelReflexion`/`-ModelEmbeddings` parameters on the real `setup.ps1` invocation in `run_windows` — both wired from the same `opts.models` map, added together with the Windows candidates support above. **Not verified against a real elevated Windows install in the session that added it** (no Windows machine/VM available - see the Windows elevation section above for the same limitation), only that the two Rust functions compile and that `run_windows`'s existing single-`pkexec`-equivalent `Start-Process -Verb RunAs` flow is otherwise unchanged.
- **Installation**/**Terminé**: driven entirely by the existing `install-step`/`install-log`/`install-done` events — progress % is `done / (total - skipped)` over the steps `run_linux`/`run_windows` already emit, not a fake timer.

## SelfLlama Launcher (`launcher/`)

A second, separate Tauri app (own `Cargo.toml`/`tauri.conf.json`/binary, not a mode of `gui/`) for day-to-day use after the install is done. Unlike `gui/`, it never touches `setup.sh`/`setup.ps1`; it talks directly to local HTTP APIs:
- `list_models` / `pull_model` / `delete_model` in `launcher/src-tauri/src/main.rs` call Ollama's own REST API (`GET /api/tags`, `POST /api/pull`, `DELETE /api/delete` on `127.0.0.1:11434`) via `reqwest::blocking` — TLS is disabled at the Cargo feature level (`default-features = false`) since only plain local HTTP is ever used.
- `pull_model` streams Ollama's NDJSON progress response line-by-line into `pull-progress` events, the same idiom `gui/` uses for child-process stdout.
- Deleting a model requires confirming a JS `confirm()` dialog first, since it's irreversible.
- `open_webui_window` duplicates `gui/`'s command of the same name (opens/focuses a window on `http://127.0.0.1:8080` via `WebviewUrl::External`) — small enough that sharing it via a crate wasn't worth the indirection for two call sites.
- `webui_service_status` / `set_webui_service`: start/stop the Open WebUI service **independent of** the LAN host setting — unlike `set_webui_lan`, they never touch `webui.env`, only the unit's running state. Linux: `systemctl --user is-active|start|stop open-webui` (`parse_systemctl_is_active`, in `launcher-core` — see below — trims stdout, falls back to `"unknown"` on empty output); a missing unit file short-circuits to `"not-installed"`/an error before calling `systemctl` at all, mirroring `set_webui_lan`'s existing `unit_installed` check (factored out as `webui_unit_installed()` and reused by both). Windows: same `run_powershell()` helper `set_webui_lan` already uses, mapping `Get-ScheduledTask`'s `State` (`Running`/`Ready`/`Disabled`) to the same `active`/`inactive`/`not-installed` vocabulary Linux returns, so the frontend never branches on platform.
- `get_lan_url`: returns `http://<lan-ip>:8080` for the LAN-toggle screen's shareable URL/QR code, via the `local-ip-address` crate (no existing IP-detection code anywhere in the repo to reuse — `toggle-webui-lan.sh`/`.ps1` don't need one, they only flip the bind address). `build_lan_url` (in `launcher-core`) brackets IPv6 addresses (`http://[::1]:8080`) since plain `format!("http://{ip}:8080")` isn't a valid URL for those.
- The frontend's QR code (shown next to the shareable URL when LAN access is on) renders client-side via `launcher/dist/qrcode.js`, a vendored copy of the MIT-licensed [`qrcode-generator`](https://github.com/kazuhikoarase/qrcode-generator) library (same one referenced in the original design mockup) — vendored rather than pulled from a CDN so the app has no runtime network dependency for something purely presentational, consistent with the zero-npm-dependency frontend convention.
- Same gitignore/Cargo.lock conventions as `gui/`, mirrored under `launcher/src-tauri/`.

### `launcher-core`: a tauri-free lib crate for `launcher/`'s pure logic

`launcher/src-tauri/src/main.rs` imports `tauri` unconditionally at the top of the file, so on Linux, compiling it at all — even just to run `cargo test` on a handful of pure string/JSON-parsing functions — pulls in the full `wry`/`webkit2gtk-sys` dependency chain, which needs `libwebkit2gtk-4.1-dev`/`libgtk-3-dev`/`libsoup-3.0-dev` installed first. `launcher/launcher-core` (a separate crate, `launcher/src-tauri/Cargo.toml` depends on it via a plain path dependency) holds every pure, tauri-free piece of logic pulled out of `main.rs`'s `#[tauri::command]`s: `to_model_info` (+ the `TagsResponse`/`RawModel`/`RawDetails`/`ModelInfo` types), `parse_systemctl_is_active`, `build_lan_url`, and `parse_webui_lan_status`/`format_webui_env` (the `webui.env` read/write logic behind `webui_lan_status`/`set_webui_lan`, previously inlined directly in those commands and untested). Its own `Cargo.toml` depends on nothing but `serde`(+`serde_json` as a dev-dependency for its tests) — no `tauri`, no `reqwest` — so `cd launcher/launcher-core && cargo test` runs in a few seconds with no system packages installed at all. `main.rs`'s commands (`list_models`, `webui_service_status`, `get_lan_url`, `webui_lan_status`, `set_webui_lan`, ...) call into these functions rather than reimplementing them; the app's actual `#[tauri::command]` wiring and I/O (HTTP calls, file reads/writes, `systemctl`) stay in `main.rs`, since those aren't the part worth unit-testing without a live Ollama/systemd session. `.github/workflows/test.yml`'s `rust-unit-tests` job reflects this split: the `gui` matrix entry still installs WebKitGTK and tests `gui/src-tauri` directly (its own unit tests — `find_marker_upwards`, `__DETECT__` JSON parsing — are in `main.rs` too, and `gui/` wasn't part of this split), while the `launcher-core` entry skips that apt install entirely and tests `launcher/launcher-core` instead; `launcher/src-tauri`'s full binary is still built and clippy'd (with WebKitGTK installed) by `rust-ci.yml`'s `clippy-and-build` job, so a compile error there still fails CI, just in a different job.

## `application/core` (SelfLlama restructure, Phase 3 — wired into `gui/` since Phase 7)

A tauri-free lib crate, same convention as `launcher-core` above: `application/core/src/detect/{gpu,ram,cpu,distro}.rs` and `application/core/src/progress/mod.rs` hold pure, tested ports of the detection and output-streaming logic currently spread across `scripts/linux/02-configure-gpu.sh`, `scripts/linux/lib/common.sh`, `scripts/windows/lib/common.ps1`, and `gui/src-tauri/src/main.rs`'s (formerly its own local, now-deleted) `stream_ansi_aware`. `application/core/Cargo.toml` depends on nothing but `serde` (+`serde_json` as a dev-dependency) — no `tauri`, no `wry`, no `webkit2gtk` — so `cd application/core && cargo test` (or `cargo test -p core` run from within that directory; there is no workspace `Cargo.toml` at `application/` yet, so `-p` only resolves from inside the package's own directory) runs in a few seconds with no system packages installed, exactly like `launcher-core`.

**Scope, deliberately narrow**: GPU vendor/name (`gpu.rs`, ported from `detect_all_gpus` + the `rocminfo`/`AMD_GFX_OVERRIDE` lookup in `configure_amd`, plus `Get-GpuVendor` for the Windows `PNPDeviceID` format), RAM (`ram.rs`, ported from `detect_ram`'s `free -g`→`free -m` fallback rounding), CPU model/thread count (`cpu.rs`, ported from `detect_cpu`), and Linux distro family/pretty name (`distro.rs`, ported from `detect_distro`; no Windows equivalent, same as the Bash/PowerShell split — Windows has no package-manager family to pick). Every function takes the text a real command would print (or, for the Windows GPU path, a list of `PNPDeviceID` strings) and returns a parsed value — none of them spawn a process or touch the filesystem, so no real GPU/distro is needed to test them. Model-tier selection (`compute_tier`, the `CAND_<TIER>_<usage>` candidate tables) is **out of scope** here on purpose: it's a decision built on top of RAM/GPU detection, not detection itself, and belongs with a future `core::install` rather than `core::detect`.

**Two "known traps" from earlier planning turned out not to exist in the code being ported**, found by reading `02-configure-gpu.sh` directly before porting rather than assuming the trap was real. One was a confirmed regression and has since been fixed in both places (see [AMD GPU handling](#amd-gpu-handling) above): `find_rocminfo()`/`resolve_rocminfo_path` now handle `rocminfo` being reachable only under `/opt/rocm*/bin` rather than `PATH`, in `02-configure-gpu.sh` and `gpu.rs` respectively, fixture-tested on both sides (no real AMD RDNA4 hardware available to validate against). The other — `configure_intel()` not distinguishing an integrated GPU from a discrete Arc card, both getting `OLLAMA_VULKAN=1`+`OLLAMA_IGPU_ENABLE=1` unconditionally — is **not** a confirmed regression, just never-implemented, never-validated behavior; see [Intel GPU handling](#intel-gpu-handling) above for why this stays undocumented-as-a-branch rather than coded, in both the Bash script and `gpu.rs`.

**Validated against this session's own real machine** (Intel Iris Xe iGPU, Pop!_OS 24.04 — `ID=pop`/`ID_LIKE="ubuntu debian"` → `debian` family), not just fixtures: `application/core/tests/real_machine_comparison.rs` (`#[ignore]`, same convention as `launcher/src-tauri`'s live-Ollama test — run with `cargo test -p core --test real_machine_comparison -- --ignored --nocapture`) feeds this machine's real `lspci`/`free`/`/proc/cpuinfo`/`/etc/os-release` output through `core::detect` and prints it next to what `02-configure-gpu.sh --detect-only`/`03-pull-models.sh --detect-only` report for the same machine. ### `core::install` (SelfLlama restructure, Phase 5 — wired into `gui/` since Phase 7, via `application::privileged`)

`application/core/src/install/{mod,ollama,gpu,webui}.rs`: pure *plans* (data + decision logic, no process spawned, no file written) ported from `01-install-ollama.sh`, `02-configure-gpu.sh`'s `configure_amd`/`configure_nvidia`/`configure_intel`, and `04-install-webui.sh`. Reuses `detect::gpu::amd_gfx_override` rather than duplicating `AMD_GFX_OVERRIDE` - GPU vendor/gfx-code *detection* stays in `detect::gpu`, only the resulting install decision lives here. Each plan-building function takes already-gathered facts (`ollama_on_path: bool`, `driver_present: bool`, `gfx: Option<&str>`, `pipx_on_path: bool`, a small local `DistroFamily` enum converted from `detect::distro`'s raw family string, ...) and returns a plan; nothing here runs `pkg_install`, writes a systemd unit, or prompts anyone - that stays `application::privileged`'s job (Phase 4), not wired to these plans yet.

**Every "known trap" was re-verified against the actual current script before writing this port, not assumed from an earlier conversation** (the same discipline that caught `find_rocminfo`/iGPU-Arc in Phase 3):
- The `write_amd_override`/`configure_nvidia` `set -e` pitfalls are still fixed in Bash exactly as before, and have **no Rust equivalent to port at all** - Rust has no implicit "a bare command's exit status becomes the function's own" propagation, so this bug class cannot recur here by construction, not by a specific design choice.
- Nvidia > AMD > Intel priority: unchanged, and not re-implemented here - it's `detect::gpu::parse_gpu_from_lspci`'s job (Phase 3), already ported and tested; `install::gpu`'s three plan functions (`nvidia_plan`/`amd_plan`/`intel_plan`) each just build the plan for a vendor `detect` already picked.
- The interactive Nvidia driver confirmation is real (`tui_yesno`/`read -r -p`, same prompt either way) and **cannot be represented as an automatic yes or no in a pure plan**: `nvidia_plan` returns `confirmation: Option<NvidiaDriverConfirmation>` carrying the exact prompt text and the distro-specific action to take if confirmed (including openSUSE's case, which is a manual instruction to the user, not a package list, ported as `DistroAction::ManualStepRequired` rather than an empty package list) - `Some` only when a driver isn't already present, `None` otherwise. Actually asking the user, and re-invoking with a decision, is left to a later phase.
- `configure_intel()` still applies `OLLAMA_VULKAN=1`+`OLLAMA_IGPU_ENABLE=1` uniformly to any Intel GPU match, iGPU or discrete Arc, unchanged since the last check - `install::gpu::intel_plan` takes no such distinction as an input at all, and a dedicated test (`intel_always_sets_both_vulkan_and_igpu_enable_uniformly`) exists specifically to make that explicit rather than leaving it implicit.
- **One confirmed, real divergence found and fixed with the user's explicit sign-off before porting**: `04-install-webui.sh`'s pip fallback (used when `pipx` isn't available) is `pip install --break-system-packages --upgrade open-webui` unconditionally on this branch today - `--break-system-packages` is Debian/PEP-668-specific and would be wrong on Arch/Fedora/openSUSE. A distro-aware fix (`--break-system-packages` on Debian, `--user` elsewhere) already exists on the unmerged `fix/comprehensive-issues` branch (along with an unrelated no-op `save_state` call removal in `configure_amd`, confirmed harmless and left as-is - no plan-level equivalent to port). Asked the user directly rather than silently picking one: `install::webui::package_install_plan` ports the **corrected** distro-aware behavior, not `refactor/selfllama-restructure`'s current literal one - see the doc comment at the top of `webui.rs` and its `pip_fallback_on_arch_fedora_opensuse_uses_user_not_break_system_packages` test. `scripts/linux/04-install-webui.sh` itself was **not** changed to match (out of scope for this phase - modifying `scripts/linux/` wasn't part of it); this is a known, tracked mismatch between the Bash script and this Rust plan until either `fix/comprehensive-issues` is merged or `04-install-webui.sh` is patched separately.

**The `EnvironmentFile=`/`${WEBUI_HOST}` point already flagged as needing care**: `webui::render_unit_content(webui_bin, env_file_path)` substitutes `webui_bin`/`env_file_path` for real (both are runtime-resolved values - `webui_bin` comes from `pipx environment --value PIPX_BIN_DIR` or `command -v open-webui`, neither of which this function runs itself, so both are parameters, not computed here) while leaving the literal string `${WEBUI_HOST}` unexpanded in `ExecStart=`, exactly matching the Bash heredoc's escaped `\${WEBUI_HOST}` - systemd substitutes it from `EnvironmentFile=` at service-start time, not this code at generation time. Directly tested (`unit_content_keeps_webui_host_as_a_literal_placeholder_for_systemd`).

**Consumed by `application::privileged` since Phase 6** (see below) — `scripts/linux/` itself remains unchanged and unaffected either way.

## `application/src-tauri` and `application::privileged` (SelfLlama restructure, Phases 4, 6 & 7)

A second new crate under `application/`, `selfllama-installer` (provisional package/binary name — the SelfLlama rename's product naming was never finalized, see the naming-audit conversation; trivial to rename later, not worth blocking this phase on). Unlike `application/core`, this one is meant to eventually hold the real Tauri app (hence living in a directory named `src-tauri`, matching `gui/src-tauri`/`launcher/src-tauri`'s convention) — but **does not depend on `tauri` yet**: nothing written so far (`application::privileged`, the only thing in it this phase) needs `AppHandle`/`#[tauri::command]`/event emission, and adding an unused dependency just because the directory name implies it would be premature. `cargo tree` from `application/src-tauri/` confirms zero `tauri`/`wry`/`webkit2gtk` in the graph — only `core` (path dependency), `serde`/`serde_json`, and (`cfg(unix)`) `libc`. The crate has both a `[lib]` (`selfllama_installer`, so `application/src-tauri/tests/*.rs` integration tests can reach `privileged::` — a binary-only crate can't be depended on by its own integration tests) and a `[[bin]]` (`src/main.rs`, a thin wrapper).

**Why this module exists**: `gui/src-tauri/src/main.rs::run_linux` spawns `pkexec` three separate times today (`01-install-ollama.sh`, `02-configure-gpu.sh`, `04-install-webui.sh --install-deps`), each its own `unix-process` subject as far as polkit is concerned. Phase 2 of this restructure confirmed empirically (real `pkexec`/polkit runs on a real session, `/proc/self/cgroup`/`/proc/self/sessionid` compared with and without `setsid()`, and `org.freedesktop.policykit.exec`'s own action definition read directly) that `org.freedesktop.policykit.exec` declares plain `auth_admin`, not `auth_admin_keep`, on every distro this project targets — there is no session-caching trick available from the app side to reduce three prompts to one; whether a real desktop's polkit agent happens to remember an earlier prompt is entirely up to that agent's own configuration, not something this app controls. The only reliable fix is architectural: **one** `pkexec` call covering the whole privileged phase, which is what `application::privileged` provides.

**How it works**: rather than building, bundling, and code-signing a second binary just for the privileged worker, `selfllama-installer` re-invokes **itself** under `pkexec`, with a sentinel argument (`privileged::RUN_PRIVILEGED_PHASE_ARG`, `--run-privileged-phase`) that `main.rs` checks for before anything else. `privileged::build_privileged_phase_command` builds that one command (`pkexec <path-to-self> --run-privileged-phase [--skip-webui]`); `privileged::spawn_privileged_phase` spawns it, reusing `detach_from_tty`/`setsid()` (a faithful, unmodified port of `gui/src-tauri`'s own `detach_from_tty` — Phase 2 confirmed this has no bearing on the polkit session question above) and the same two-reader-thread shape `gui/src-tauri`'s `stream_child` already uses to avoid a pipe-buffer deadlock, streaming output (via `core::progress::stream_ansi_aware`, unmodified) back through an `mpsc::Receiver<PhaseLine>` instead of directly emitting Tauri events, since this crate has no `AppHandle` yet.

Inside the single privileged process, `privileged::steps::run_steps` runs `privileged::steps::default_privileged_steps` (ollama, then gpu, then — unless `--skip-webui` — webui-deps; **this exact order is load-bearing**, matching `run_linux`'s current order rather than any other listing, because `02-configure-gpu.sh`'s last step restarts the `ollama` service if already active, which assumes Ollama is already installed) in sequence, stopping at the first failure rather than continuing silently, and reports every transition (running/done/failed/needs-confirmation, with an error message on failure) to the parent as a `__STEP__{...}` JSON line on its own stdout — same idiom as `02-configure-gpu.sh`'s `__DETECT__{...}` line, just for step boundaries instead of a one-shot result, parsed back out by `privileged::protocol::parse_step_event`. That protocol module is pure (string in, `Option<StepEvent>` out) like everything in `core::progress`, and would be a reasonable candidate to move into `application/core` once this design is proven out — kept in `application/src-tauri` for this phase only because touching `application/core` was out of scope here.

**Since Phase 6, each step actually runs `core::install`'s real plans** (Phase 5) instead of printing a placeholder line: `privileged::steps::{ollama,gpu,webui}.rs` gather the facts each plan needs (`command -v`-equivalent checks via `exec::command_exists`/`resolve_on_path`, `lspci -nnk`, `/etc/os-release`, `rocminfo`'s resolved path/output, `nvidia-smi`) by reusing `core::detect::{gpu,distro}` on real command output, build the plan via `core::install::{ollama,gpu,webui}`, then actually run it via `privileged::exec` (`pkg_install_commands` ports `lib/common.sh`'s `pkg_install` per distro, minus the now-redundant `sudo` — this process already runs as root; every spawned command inherits this process's own stdio via `Stdio::inherit()` rather than being captured and re-printed, so a real package manager's silence during its network phase — 30-100+s is normal on `pacman`/`dnf`/`zypper`, per Phase 2 — reaches the parent exactly as it would in a real terminal, with no timeout layered on top anywhere). `webui.rs` only wires up `core::install::webui::deps_plan` (`04-install-webui.sh --install-deps`'s prerequisites-only scope, matching what `application::privileged`'s "webui-deps" step has always meant, in both Phase 4 and today) — `core::install::webui`'s other functions (installing Open WebUI itself, the unit file) belong to the *unprivileged* run of `04-install-webui.sh`, never part of `application::privileged`'s three steps, unaffected by any of this. Real, hard-to-fake-around evidence this actually wires up correctly: running the "ollama" step's own unit test on this session's real dev machine (no root) found Ollama really already installed and really answering on `127.0.0.1:11434`, and the "gpu" step really detected this machine's real Intel iGPU via real `lspci` before failing on a real (permission-denied, no root) `apt-get` call - exactly the failure mode expected outside `pkexec`, not a logic bug.

**The Nvidia "driver missing, needs confirmation" case (`core::install::gpu::NvidiaPlan.confirmation`, Phase 5) is exposed, not resolved, exactly as that phase's task asked**: `steps::StepRunError` has two variants, `Failed(String)` and `NeedsConfirmation(ConfirmationRequest)` (a new `protocol::ConfirmationRequest` — prompt title/message plus a human-readable summary of what confirming would do, e.g. `"install packages: nvidia, nvidia-utils"` or openSUSE's manual-step message) - `steps::gpu::run_nvidia` returns the latter as soon as it sees `plan.confirmation.is_some()`, *before* installing anything. `run_steps` still stops the sequence either way (there is nothing sensible to run afterwards without an answer), but reports a distinct `protocol::StepStatus::NeedsConfirmation` (not `Failed`) in the `__STEP__` line, carrying the full `ConfirmationRequest` - so a future interactive caller (`gui/`, out of scope here) can tell "something went wrong" apart from "a decision is needed" by inspecting the wire protocol, without this phase inventing a re-invocation/answer-submission mechanism for the eventual "yes" path. Directly tested at both layers: `steps::tests::a_needs_confirmation_step_also_stops_the_sequence_but_is_reported_distinctly` (Rust-level) and `real_plans_end_to_end.rs`'s `nvidia_without_a_driver_stops_the_sequence_with_needs_confirmation_not_a_silent_install` (wire-level, real Nvidia-vendor `lspci` output, no `nvidia-smi` on the fake `PATH` — confirms no package is ever installed without a confirmed decision, and that `webui-deps` never runs afterwards).

**Windows is out of scope for this module, on purpose, not an oversight**: `setup.ps1` is already invoked as a whole via a single `Start-Process -Verb RunAs` in `gui/src-tauri/src/main.rs::run_windows` — UAC elevation keeps the same user account, so there was never a "three separate elevated processes" problem to fix there. `application::privileged` has no Windows code path at all.

**Tested without any real privileges** (aside from the one dev-machine unit test noted above, which fails safely and instructively without root rather than needing it): 23 unit tests (command/plan-to-`Command` construction in `exec.rs`, the `__STEP__`/`NeedsConfirmation` protocol round trips, `run_steps` stopping at the first failure or unresolved confirmation and never running later steps, using injected closures to record execution order — no real `pkexec`, no real package manager for these) plus 4 integration tests across two files. `tests/single_pkexec_call.rs` (Phase 4, still passing unchanged) spawns a fake `pkexec` that only logs its invocation and exits, to count calls cheaply. `tests/real_plans_end_to_end.rs` (Phase 6) goes further: its fake `pkexec` really `exec`s its arguments, truly re-invoking the real, freshly-`cargo test`-built `selfllama-installer` binary (located relative to `std::env::current_exe()`, since that call inside an integration test returns the *test* binary's own path, not the `[[bin]]`'s) with `--run-privileged-phase` - so the real `steps/*.rs` code runs for real, against a `PATH` of fakes for every external tool it would otherwise shell out to (`lspci`, `rocminfo`, `ollama`, `systemctl`, `curl`, `pacman`, `pipx`) plus `OS_RELEASE_FILE`/`ROCM_OPT_DIR`/`OLLAMA_SERVICE_OVERRIDE_PATH` overrides (`spawn_privileged_phase` gained an `extra_env` parameter for this, generalizing Phase 4's `path_override` - same "scoped to the one spawned child via `Command::env`, never `std::env::set_var`" rationale). One scenario (Arch, AMD RDNA4 needing the HSA override, Ollama already present, pipx already present) confirms, byte-for-byte: `pacman` was really invoked with `core::install::gpu::amd_plan`'s exact Arch package list (not a placeholder), and the systemd drop-in was really written with the exact `HSA_OVERRIDE_GFX_VERSION=11.5.0` content that plan's `override_action` specifies - plus every `__STEP__` line reaching `"status":"done"` and zero remaining `(stub)` output anywhere in the stream. A second scenario is the Nvidia-needs-confirmation case described above.

### `gui/src-tauri` consumes `application::privileged` (Phase 7)

**`gui/src-tauri/src/main.rs::run_linux` no longer spawns `pkexec` itself, three times or otherwise.** `gui/src-tauri/Cargo.toml` gained two path dependencies — `selfllama-installer = { path = "../../application/src-tauri" }` and `selfllama-core = { package = "core", path = "../../application/core" }` — confirmed via `cargo tree` before/after to introduce zero new third-party crates (only the two internal path crates, whose own transitive deps — `serde`/`serde_json`/`libc` — were already present in `gui/src-tauri`'s graph and simply deduped). `run_linux` now does one thing where it used to do three: build a single `application::privileged::PrivilegedPhaseOptions`, call `spawn_privileged_phase` once, and translate the resulting `__STEP__`/plain-text stream into the exact same `install-log`/`install-step` Tauri events the frontend already listened for — the wire protocol changed underneath, the JS-visible contract didn't (aside from the new event described below). The models/webui *unprivileged* steps after it (`03-pull-models.sh`, `04-install-webui.sh` without `--install-deps`) are untouched — Phase 7's scope was specifically the three-`pkexec` privileged sequence, not the whole install flow.

**The `core` naming collision, found and fixed the hard way**: naming the dependency literally `core` (matching `application/core/Cargo.toml`'s actual package name) compiles fine in `application/src-tauri` (no proc macros there expecting `::core::` to mean the standard library) but breaks every `#[tauri::command]`/`tauri::generate_handler!`/`tauri::generate_context!` invocation in `gui/src-tauri` with `error[E0433]: cannot find 'option' in 'core'` — those macros' expansions reference `::core::` assuming it resolves to Rust's own standard-library crate, and a dependency literally named `core` shadows that. Fixed with Cargo's dependency-rename syntax, `selfllama-core = { package = "core", path = "../../application/core" }`, referenced in code as `selfllama_core::` — `application/core/Cargo.toml`'s own package name was deliberately left as `core` (out of scope to rename it there just to work around a problem specific to this one consumer).

**`gui/src-tauri` gained a `[lib]`/`[[bin]]` split it didn't have before**, mirroring `application/src-tauri`'s own shape and for the same reason: a binary-only crate can't be depended on by its own `tests/*.rs` integration tests, and Phase 7's task explicitly asked for a real integration test proving one `pkexec` call *from `gui/src-tauri`'s own code*, not just re-pointing at `application/src-tauri`'s existing proof of the same mechanism for a different binary. `src/main.rs` is now a thin wrapper: it checks `std::env::args()` for `selfllama_installer::privileged::RUN_PRIVILEGED_PHASE_ARG` before anything else and, if present, runs `selfllama_installer::privileged::run_privileged_worker` and exits — without this check, `pkexec` re-invoking `selfllama-gui` (the same self-re-invocation trick `application::privileged` already uses, see above) would try to launch a second full Tauri/GTK window as root instead of running the privileged worker code. Everything else — `run_linux`/`run_windows`, the Tauri commands, `run_tauri_app()` (renamed from the old `fn main()`'s body) — moved into `src/lib.rs` unchanged in behavior.

**A second, unrelated Tauri-macro gotcha surfaced during the same split**: marking `detect_system`/`run_install`/`open_webui_window` `pub fn` (so `main.rs` could plausibly reference them, before it was clear it didn't need to) produced `error[E0255]: the name '__cmd__detect_system' is defined multiple times` — `#[tauri::command]`'s hidden generated items collide with themselves when the function is `pub` in the same module as the `tauri::generate_handler!` call that registers it. Fixed by reverting all three back to plain (private) `fn`; `run_tauri_app()` (which contains the `generate_handler!` call) lives in the same file, so private visibility was already sufficient and no `pub` was ever actually required.

**The Nvidia "needs confirmation" case is resolved here, at the `gui/` layer, with a real UI interaction — never auto-confirmed nor auto-rejected**, per Phase 7's explicit constraint. `run_linux` returns a new `InstallOutcome` enum (`Completed` or `NeedsConfirmation(ConfirmationPayload)`) instead of a bare `Result<(), String>`; `run_install` matches on it and, for the confirmation case, emits a **new** Tauri event, `install-confirmation-needed` (payload: `ConfirmationPayload { promptTitle, promptMessage, actionDescription }`, camelCase via `#[serde(rename_all = "camelCase")]`, converted from `application::privileged::protocol::ConfirmationRequest`'s snake_case fields the same way `DetectResultRaw`→`DetectResult` already converts the scripts' own JSON) — and deliberately does **not** emit `install-done` in this case, since the install hasn't finished or failed, it's paused on a decision only the user can make. `gui/dist/main.js` listens for this event and shows a real `window.confirm()` dialog built from the three fields — the same plain-`confirm()` pattern `launcher/dist`'s existing model-deletion confirmation already uses for irreversible actions (see [SelfLlama Launcher](#selfllama-launcher-launcher) above), reused here rather than inventing a new dialog component. Accepting re-invokes `startInstall({ confirmNvidiaDriverInstall: true })`, which threads a new `confirmNvidiaDriverInstall` field through `InstallOptions` into a **second**, deliberate `PrivilegedPhaseOptions.confirm_nvidia_driver_install = true` and a **second** full `spawn_privileged_phase`/`pkexec` call — a one-shot privileged worker process has no way to pause mid-sequence and resume from an in-process prompt, so "confirm and continue" is necessarily a fresh, second privileged phase, not a resumed first one; declining just records a local `installDone`-shaped failure state and appends a log line, with no second call at all. This mirrors `application::privileged`'s own Phase 6/7 design (`PrivilegedPhaseOptions.confirm_nvidia_driver_install`, `steps::gpu::run(confirm_nvidia_driver_install)`) one layer up, at the Tauri-event boundary instead of the wire-protocol boundary.

**Proven with a real integration test, same style as Phase 4/6's**: `gui/src-tauri/tests/single_pkexec_call.rs` calls a new `pub fn run_privileged_phase_raw` (extracted out of the `AppHandle`-based `run_privileged_phase` specifically so a test without a live Tauri app can call it) against a fake `pkexec` that really `exec`s its arguments, re-invoking the real, freshly-built `selfllama-gui` binary (located the same `target/debug/<bin>`-relative-to-the-test-binary way `application/src-tauri`'s own tests already do, since `std::env::current_exe()` inside an integration test returns the test harness's own path) with `--run-privileged-phase`, against a `PATH` of fakes for every tool the real steps shell out to. Confirms exactly one logged `pkexec` invocation, with the exact args `<path-to-selfllama-gui> --run-privileged-phase`, and that all three steps (`ollama`/`gpu`/`webui-deps`) really reach `"status":"done"` — not a stub. `OLLAMA_SERVICE_OVERRIDE_PATH` had to be added to the test's env overrides after a first run tried to touch the real, root-only `/etc/systemd/system/ollama.service.d/override.conf` on the "no dedicated GPU" branch.

**Full cross-crate test count after Phase 7**: `application/core` 70/70 (unchanged), `application/src-tauri` 24 unit + 2 (`single_pkexec_call.rs`) + 3 (`real_plans_end_to_end.rs`, including the new `nvidia_confirmed_on_a_second_call_actually_installs_the_driver`) = 29/29, `gui/src-tauri` 6 unit (unchanged — the local `stream_ansi_aware` tests were deleted along with the function itself, now covered by `application/core`'s own suite) + 1 (`single_pkexec_call.rs`) = 7/7. `launcher/` was not touched at all in this phase (confirmed via `git status --short launcher/`).

**Manual end-to-end verification, actually run once for real (not just documented as a should-do)**: with a throwaway `$HOME` and a real `cargo build`-produced `selfllama-gui` binary, launched on this session's own real desktop (Pop!_OS 24.04, Intel Iris Xe iGPU) and driven through the wizard by a human (not automated), the Installation step really showed exactly **one** polkit password prompt for the whole privileged phase (ollama + gpu + webui-deps together), confirmed independently via `journalctl` (one `polkitd` "successfully authenticated" line, one `pkexec: Executing command ... --run-privileged-phase` line) rather than only inferred from the app's own UI — the property this whole restructure exists to deliver, now proven outside any test harness. This run went further than originally planned (authentication was completed for real rather than declined at the prompt) and surfaced a real architectural gap in what `$HOME` isolation actually covers — see [Limits of `$HOME` isolation for manual testing](#limits-of-home-isolation-for-manual-testing) below, added specifically because of what this run revealed. On a machine with a discrete Nvidia GPU and no driver installed, the sequence should instead stop after the "gpu" step reaches `needs-confirmation`, pop the `window.confirm()` dialog with the real prompt/action text sourced from `core::install::gpu::nvidia_plan`, and only ask for a *second* polkit prompt if the dialog is accepted — declining should leave the install visibly stopped with no further prompt. This specific sub-case still has not been run for real in any session (no discrete Nvidia hardware available, same limitation Phase 5/6 already noted for `core::install::gpu`'s Nvidia path) — the Rust-level proof above (`nvidia_confirmed_on_a_second_call_actually_installs_the_driver`, `nvidia_without_a_driver_stops_the_sequence_with_needs_confirmation_not_a_silent_install`) is what stands in for it.

### Limits of `$HOME` isolation for manual testing

A real manual run of the wizard through to a completed, authenticated privileged phase (see above) confirmed the single-pkexec property, but also showed that an isolated `$HOME` protects *less* of the host machine than it might appear to. Written down here so no developer, future Claude Code session, or the author months from now assumes a throwaway `$HOME` fully sandboxes a manual test the way it sandboxes the automated integration tests (which use `OS_RELEASE_FILE`/`ROCM_OPT_DIR`/`OLLAMA_SERVICE_OVERRIDE_PATH` env overrides that the real, shipped app has no equivalent of — see [`application/src-tauri` and `application::privileged`](#applicationsrc-tauri-and-applicationprivileged-selfllama-restructure-phases-4-6--7) above).

**Root cause**: Ollama runs as a single, machine-wide system service (`ollama.service`, one instance per machine) with no concept of a per-user or per-`$HOME` isolated instance — it is not something a test can spin up a throwaway copy of just by pointing `$HOME` elsewhere.

**Concretely, not isolated by a throwaway `$HOME`**:
- `/etc/systemd/system/ollama.service.d/override.conf`: written for real by the privileged "gpu" step regardless of which `$HOME` the calling process used, since this path is fixed and system-wide, not derived from `$HOME` at all.
- The real `ollama.service` itself gets **really restarted**: `restart_ollama_if_active()` (`application/src-tauri/src/privileged/steps/gpu.rs`, function `run` at line 27, `restart_ollama_if_active` at line 194 at the time of writing — shifted since this note was first written, by the silent-phase-indicator work below) runs `systemctl restart ollama` unconditionally whenever the service is already active at that point in the sequence — regardless of whether the override content actually changed. Confirmed in this session's real run via `journalctl`: the service's `Main PID` changed and its "active since" timestamp reset to the moment the gpu step ran, even though the override file's *content* came out byte-for-byte identical to what was already there.
- Models pulled by `03-pull-models.sh` (the unprivileged step that runs after the privileged phase): these go through Ollama's own HTTP API (`POST /api/pull`) to the one real, shared daemon, and land in that daemon's real, system-wide model store (`/usr/share/ollama/.ollama/models` on this machine) — not anywhere under the test's `$HOME`. A real run for the detected tier really downloads real models at their real size (confirmed: this session's tier-S run really pulled `nomic-embed-text`, `qwen2.5-coder:7b`, `deepseek-r1:7b`, `llama3.1:8b`, ≈14.6 GB total, verifiable afterwards with a plain `ollama list`).

**What a throwaway `$HOME` *does* correctly isolate**: `~/.config/selfllama/` (`state.env`, `webui.env`), and the Open WebUI **user** systemd service — `systemctl --user` unit lookup follows the search paths of the real, already-running `systemd --user` manager for that login session (which does not change with a child process's `$HOME` env var), so a script run under a throwaway `$HOME` writes its own `~/.config/systemd/user/open-webui.service` unit file into that throwaway tree, but any `systemctl --user enable/start` call it makes still talks to the one real user-session manager, which resolves the *real* unit by name from its own real search path — confirmed in this session's run: the real Open WebUI service's PID never changed throughout. Anything else that is genuinely per-user, per-`$HOME` application state (not backed by a single shared system-level daemon) is isolated the same way.

**Recommendation for any future manual test that might reach the privileged phase**: check `systemctl status ollama` *before* starting (note whether it's active, and its current `Main PID`/override content), and go in expecting that a real, completed authentication will cause a few seconds of real service downtime during the restart and, if the run proceeds to model pulls, real disk space and bandwidth usage for whatever the detected tier pulls. Neither of those is a bug in `application::privileged`/`core::install::gpu` — the unconditional restart is an intentional, already-reviewed design choice (see the Phase 4/6 sections above) — but a manual tester who expects a `$HOME` override to make the run fully inert on a machine with a real, already-configured Ollama install would be wrong to assume so, and should plan the test accordingly (e.g. run it on a machine/VM with no pre-existing Ollama install, or accept and budget for the brief restart and the real download).

### Silent-phase indicator for `pacman`/`dnf`/`zypper` (package-manager silence, not a hang)

Closes a gap left open since Phase 2's investigation (see [Limits of `$HOME` isolation](#limits-of-home-isolation-for-manual-testing) above and the earlier paragraphs on `stream_ansi_aware`): `pacman`/`dnf`/zypper's network-install phase announces the whole transaction and then prints nothing at all for 30–100+ seconds (sometimes longer) until it finishes — confirmed real, not a hang, but with nothing in the `install-log` pane during that stretch to tell a user the difference. `apt-get` (per-file + `\r`-driven `dpkg` progress) and `curl` (a continuous `\r` percentage bar) were already fine: `core::progress::stream_ansi_aware` (unchanged by this) surfaces both live.

**Deliberately a separate mechanism from `stream_ansi_aware`, not folded into it**: `stream_ansi_aware` reacts to *what a command prints*; this problem is the opposite — a command that's about to print *nothing* for a long time. Detecting "no output for N seconds" and inferring a hang from it is exactly the pattern CLAUDE.md's Phase 2 conclusion rules out (see above) — silence duration is never measured or acted on anywhere in this codebase. Instead, `exec::is_known_silent_package_manager(program)` (`application/src-tauri/src/privileged/exec.rs`) is a static, pure lookup — `pacman`/`dnf`/`zypper` → `true`, everything else (`apt-get`, `curl`, `systemctl`, `ollama`, `sh`, ...) → `false` — checked once, *before* a command is even spawned, never based on anything it does or doesn't print afterwards.

**Wiring**: `exec::run_commands_reporting_silent_phase(commands, on_silent_phase)` is the same execution loop as the existing `run_commands` (now a thin wrapper delegating to it with a no-op callback — zero behavior change for its other callers, `systemctl daemon-reload`/`restart` in `steps/gpu.rs`, `systemctl enable --now` in `steps/ollama.rs`), except it calls `on_silent_phase(program)` right before running any command `is_known_silent_package_manager` recognizes. The four call sites that actually run `pkg_install_commands`'s output (`steps/gpu.rs`'s Nvidia-confirmed-install/AMD/Intel branches, `steps/webui.rs`'s deps install) pass a closure that calls a new `steps::emit_running_silent(id, label, message)` — emitting a `protocol::StepEvent` with a new `StepStatus::RunningSilent` variant and a new `message: Option<String>` field (`Some` only for this status, omitted from the wire format otherwise — every existing `Running`/`Done`/`Failed`/`NeedsConfirmation` `__STEP__` line is byte-for-byte unchanged). `exec::silent_phase_message(program)` builds the static text (`"Running pacman - this can take a while with no output, which is expected and not a hang."`) — plain English, no percentage, no spinner tied to a fake number. `steps/mod.rs` gained `GPU_STEP_ID`/`GPU_STEP_LABEL`/`WEBUI_DEPS_STEP_ID`/`WEBUI_DEPS_STEP_LABEL` constants (plus the same for `ollama`) so `default_privileged_steps` and these mid-step emissions share one source of truth for each step's id/label rather than duplicating the literal strings.

**`gui/src-tauri`**: `run_privileged_phase` maps `PrivStepStatus::RunningSilent` to the wire string `"running-silent"` and now threads `event.message` through (`InstallStep` gained a `message: Option<String>` field, `emit_step` is unchanged and still passes `None`; a new `emit_step_with_message` is what the `__STEP__`-parsing call site actually uses, since it's the only one with a message to send).

**`gui/dist`**: a new static status line (`#install-silent-status`, hidden by default) sits between the progress bar and the scrolling log pane — a plain sentence, not another line in the log stream and not a second progress bar. `main.js`'s `install-step` listener shows it (with the backend's message) when `status === 'running-silent'`, and hides it again the moment *either* a real `install-log` line arrives (proof the silence actually ended) *or* the next `install-step` event fires for any step (a state transition already supersedes it) — whichever happens first, matching the task's "stays shown until real output or the command ends" requirement without polling or timing anything client-side either.

**Tested**: `exec.rs` gained unit tests confirming `is_known_silent_package_manager` is `true` only for `pacman`/`dnf`/`zypper` (and explicitly `false` for `apt-get`/`curl`, plus other commands this module shells out to), that `run_commands_reporting_silent_phase` invokes its callback before attempting to spawn `pacman` (which isn't installed on this dev machine or its CI, so the spawn itself fails fast — irrelevant to what's being tested: the callback firing *before* that attempt) and does *not* invoke it for a real, successfully-attempted `apt-get`/`curl` call (both exit fast with a usage message and no network access when run with no arguments, safe to actually execute in a test). `protocol.rs` gained a round-trip test for a `RunningSilent` event carrying a message, and a test asserting its JSON never contains `"percent"`/`"progress"` — the "no fabricated number" constraint checked directly against the wire format, not just by convention. `application/src-tauri`: 39/39 (was 29/29 after Phase 7 — 8 new `exec.rs` tests, 2 new `protocol.rs` tests). `gui/src-tauri`: 7/7 unchanged (this feature added no new Rust-level tests there beyond what compiling against the changed `application/src-tauri` types already proves; the frontend behavior was verified with `node --check gui/dist/main.js` only, no live-browser/WebDriver run in this session — see [E2E/UI tests](#e2eui-tests-guie2e-tests-launchere2e-tests) above for why that needs `webkit2gtk-driver`/`xvfb`, not installed in this session's environment).

### Windows elevation: known gap, verification pending

An audit session read `scripts/windows/setup.ps1`, `scripts/windows/lib/common.ps1`, and `gui/src-tauri/src/lib.rs::run_windows` end to end specifically to check whether Windows has anything equivalent to the Linux "three separate `pkexec` calls" problem `application::privileged` was built to fix — rather than assuming a Linux/Windows parallel applies automatically, per this restructure's own established discipline (see the `resolve_rocminfo_path`/Intel-iGPU notes above). No Windows machine or VM was available in that session, so this is a read-only code audit, not an empirical test — the checklist below exists specifically to close that gap once a Windows environment is available.

**Current state (confirmed by reading the code)**:
- **Exactly one elevation point exists, and it is already correctly scoped.** Neither `setup.ps1` nor `lib/common.ps1` contains any elevation logic at all (`grep -rn "RunAs\|Verb\|elevat\|UAC" scripts/windows/` returns nothing) - they simply assume whatever privilege level they were launched with. The single elevation call lives entirely in `gui/src-tauri/src/lib.rs::run_windows`: `Start-Process -FilePath powershell.exe -Verb RunAs -Wait -ArgumentList <all of setup.ps1's args>`, wrapping the *entire* script (Ollama install, models, Open WebUI) in one prompt. There is no "three prompts" problem to fix here, and there never was, on the Windows side - this part needs no work regardless of what the checklist below finds.
- **A real, but different-in-kind, UX gap does exist**: `Start-Process -Verb RunAs` is structurally incompatible with PowerShell's stdout/stderr redirection (`-RedirectStandardOutput`/`-RedirectStandardError`/`-RedirectStandardInput` cannot be combined with `-Verb` - a documented constraint, since verb-based elevation requires `UseShellExecute=true`, and `UseShellExecute=true` is incompatible with .NET stream redirection). Concretely: `run_step`'s `Stdio::piped()` capture only ever sees the *outer* one-line wrapper command's own output (which is essentially nothing), never `setup.ps1`'s real output (winget, `ollama pull`, Open WebUI install messages) - that goes to a separate console window Windows itself opens for the elevated process, never reaching the app's own log pane. The existing `InstallStep` comment (`gui/src-tauri/src/lib.rs`, the "Drives the frontend's step indicator" note above `struct InstallStep`) already hints at this ("we can't see inside that process's own progress") but only frames it as a granularity limit (one step instead of four); the audit's finding is stronger: the log pane isn't just coarse, it's *empty* for the whole duration of a potentially multi-minute install. This is a UX gap, not a reliability bug - no hang, no repeated password prompt, `-Wait` returns normally.
- **The unresolved, more consequential question: is this elevation even necessary at all?** Re-reading every action `setup.ps1` actually performs - `winget install` (typically user-scope), `pip install --user`/`pipx install` (explicitly per-user), `[Environment]::SetEnvironmentVariable(..., 'User')` (HKCU, never needs elevation), `Register-ScheduledTask` with no elevated run level (registers in the *current* user's own task context) - none of them structurally appear to need administrator rights, unlike Linux's real `pkg_install`/system-level systemd units. The commit that introduced this elevation (`5fe3ff7`, `feat: add Tauri desktop GUI orchestrating setup.sh/setup.ps1`) justifies it only by analogy to the Linux per-user-state problem ("UAC elevation keeps the same user account so there's no equivalent problem there") - it never demonstrates elevation is actually *required*, and its own commit message says outright: "Did not exercise a real install (pkexec) against this machine." In other words: this elevation has never been empirically validated as necessary, on either platform's original commit.

**Explicit decision, regardless of what the checklist below finds**: do **not** port `core::install`/`application::privileged` to Windows. That module exists specifically to solve the three-`pkexec`-calls-plus-misplaced-per-user-state problem, which this audit confirms does not exist on Windows (there is already exactly one elevation point, and UAC never misplaces per-user state the way `pkexec`-as-root did on Linux). Building a Windows equivalent would be solving a problem that isn't there.

**Verification checklist, to run in this exact order once a Windows machine or VM is available**:
1. `winget show --id Ollama.Ollama` - check the package's declared install scope (user vs. machine). This is the one concrete unknown left by this audit: if it declares machine scope, that alone could make elevation genuinely necessary for at least that one step, regardless of everything else in the script.
2. Temporarily remove `Start-Process -Verb RunAs` from `run_windows` (or just run `setup.ps1` directly, unelevated, from a plain PowerShell prompt) and run the real install end to end. Watch specifically for any step failing with an access-denied/permission error - `winget install`, `Register-ScheduledTask`, or anything else.
3. **If nothing fails without elevation**: remove `Start-Process -Verb RunAs` from `run_windows` permanently and call `setup.ps1` directly, the same way `run_linux` already spawns its own child processes directly. This resolves the streaming gap as a side effect, for free - an unelevated child process's stdout/stderr redirects normally, so `run_step`'s existing `Stdio::piped()` capture would start working for Windows exactly like it already does for Linux, with no Rust/UI changes beyond deleting the `Start-Process -Verb RunAs` wrapper itself.
4. **If at least one step genuinely fails without elevation**: implement the targeted fix, not a full port - have `setup.ps1` write its own output to a file (`Start-Transcript`, or redirecting each `Write-Host`-equivalent call with `*>>`), and have the *unelevated* PowerShell process (the one `gui/src-tauri` already spawns and captures via `Stdio::piped()`) tail that file, relaying new lines into `emit_log` as they appear. This is a known workaround for exactly this `-Verb RunAs`/redirection incompatibility, and is a small, self-contained change - not a Rust port of `application::privileged`, which remains out of scope per the decision above either way.

## Releases

The root `package.json` is release tooling only (commitlint, husky, semantic-release) — it is not a JS project and has nothing to do with `gui/`/`launcher/`'s frontends, which still have zero npm dependency of their own.

- **Commit messages must follow [Conventional Commits](https://www.conventionalcommits.org/)** (`feat:`, `fix:`, `docs:`, `chore:`, ...), enforced locally by a husky `commit-msg` hook running `commitlint` (`commitlint.config.js`, extends `@commitlint/config-conventional`). Run `npm install` once at the repo root to activate the hook (`prepare` script sets it up).
- **`.github/workflows/release.yml`** runs `semantic-release` whenever `ci.yml`'s `release` job calls it — `on: workflow_call`/`workflow_dispatch`, no push trigger of its own (see [Tests](#tests) above): `ci.yml` restricts that job to `push` to `main` (i.e. whenever `dev` is promoted to `main`) and gates it on `needs: [lint, test, rust-ci, e2e]`, so semantic-release only ever runs against a commit that has already passed the full CI pipeline. It inspects commits since the last release to decide the version bump (`fix:` → patch, `feat:` → minor, `BREAKING CHANGE:` footer → major), updates `CHANGELOG.md`, and creates both a `vX.Y.Z` git tag and a GitHub Release (`.releaserc.json`). It does **not** publish anything to npm (`package.json` has `"private": true`, and the plugin list in `.releaserc.json` omits `@semantic-release/npm`). Runs via [`cycjimmy/semantic-release-action`](https://github.com/cycjimmy/semantic-release-action) (not a raw `npx semantic-release` call) purely to get its `new_release_published`/`new_release_git_tag` step outputs — `.releaserc.json`/`package.json` still drive the actual release config, unchanged.
- **`.github/workflows/build-desktop.yml`** triggers on a `vX.Y.Z` tag push (also available via manual `workflow_dispatch` for testing the build step alone) and builds `gui/` and `launcher/` for Linux (`.deb`/`.rpm`/`.AppImage`, on `ubuntu-22.04` for broad glibc compatibility) and Windows (`.msi`/`.exe`) via [`tauri-apps/tauri-action`](https://github.com/tauri-apps/tauri-action), attaching the bundles to the release semantic-release just created. The tag `semantic-release` itself pushes is authenticated with the default `GITHUB_TOKEN`, which GitHub Actions deliberately excludes from triggering other workflows' `push` events (anti-recursion) — confirmed the hard way: `v1.0.0`, the first real release, got a tag and a GitHub Release with **zero** attached assets, since `build-desktop.yml` never fired. `release.yml` looks up the new release's numeric ID (`gh api repos/.../releases/tags/<tag> --jq .id`) and passes it through as `build-desktop.yml`'s `release_id` input via `gh workflow run build-desktop.yml --ref <tag> -f release_id=<id>` (gated on `new_release_published == 'true'`), instead of relying on the tag-push trigger alone — `workflow_dispatch` is expressly exempt from that restriction, which is why this works without a Personal Access Token.
  - **Why `release_id`, not just `tagName`**: `v1.1.0` (the first release built after the `ci.yml` reorg) surfaced a real bug — the matrix has 4 jobs (`gui`/`launcher` × Linux/Windows) all attaching to the *same* release, and passing only `tagName` makes `tauri-action` look the release up by tag and unconditionally overwrite its name/body every time (confirmed in `tauri-action`'s own source: `getOrCreateRelease` calls `updateRelease` whenever a non-draft release already exists for that tag). Four jobs racing to overwrite the same two fields meant whichever finished last won — `v1.1.0` ended up titled "gui v1.1.0" with a body of literally "Bundles for gui. See the release notes above for what changed.", clobbering semantic-release's actual generated notes. Passing `releaseId` instead skips that lookup/update path entirely (`tauri-action` only calls `getOrCreateRelease` `if (tagName && !releaseId)`), so the real flow never touches the release's name/body at all; `releaseName`/`releaseBody` in the workflow are only a fallback for a manual `workflow_dispatch` test run with no `release_id` given.
  - **`releaseAssetNamePattern: "ollama-${{ matrix.app }}-[version]-[platform]-[arch][ext]"`** gives every bundled format the same structure (`selfllama-gui-1.1.0-linux-x64.deb`, `selfllama-gui-1.1.0-windows-x64.msi`, ...) instead of each bundler's own default convention (RPM/deb/NSIS/WiX all name things differently by default) — `[version]`/`[platform]`/`[arch]`/`[ext]` are `tauri-action`'s own template placeholders (see its `Artifact` type), not something this repo parses itself.
  - **App version is now stamped from the release tag at build time**: a `Sync app version to release tag` step (guarded by `if: inputs.release_id != ''`, so a manual test dispatch doesn't touch it) rewrites `${{ matrix.app }}/src-tauri/tauri.conf.json`'s `version` field to the tag's version (`jq --arg v "$version" '.version = $v' ...`) right before the build, purely in that job's own checkout — never committed back to the repo. A *released* installer's version therefore matches its release tag; only a from-source build (`cargo tauri build` outside CI, or `cargo run`) still shows whatever `tauri.conf.json` has committed (`0.1.0` at the time of writing) — see the note below.
- The `version` field committed inside `gui/src-tauri/tauri.conf.json` / `launcher/src-tauri/tauri.conf.json` is **not** kept in sync with the release tag — the two apps aren't independently versioned yet, so this stays whatever it was last set to (`0.1.0` at the time of writing) between releases. `build-desktop.yml` overwrites it ephemerally at build time for actual release builds only (see above), so this gap only shows up for a local from-source build.
- `gui/src-tauri/icons/` and `launcher/src-tauri/icons/` each hold a full icon set (`32x32.png`, `128x128.png`, `128x128@2x.png`, `icon.ico`, `icon.png`) generated with ImageMagick (`convert ... -define icon:auto-resize=... icon.ico`), required by the Windows bundler (`.ico`) and recommended for the Linux ones; both `bundle.active` are `true` with `bundle.targets: "all"` so the bundler picks whatever formats are valid for the OS it runs on. The source PNGs must be 8-bit (`convert ... -depth 8`): Tauri only embeds `icon.ico` as the `.exe`'s resource on Windows, so a 16-bit PNG passes silently on Linux but breaks the Windows build alone (`failed to decode icon ...: Unsupported PNG bit depth: Sixteen`) — this was invisible until `build-desktop.yml`'s first real Windows run (`v1.0.1`), since no earlier release had actually exercised that job.

## Showcase site (`docs/`)

A single self-contained `docs/index.html` (no build step, same zero-npm-dependency convention as `gui/`/`launcher/`, and the same design tokens — see [Design tokens](#design-tokens-guidiststylecss-mirrored-in-launcherdiststylecss) above) presents the project publicly. `vercel.json` (`{"outputDirectory": "docs"}`) points Vercel at that folder; deploys are automatic via Vercel's own Git integration (not a GitHub Actions workflow) — every push gets its own preview deployment, and the production domain updates as soon as a change lands on `main`. **The production domain is `selfllama.vercel.app`, not `ollama-configuration.vercel.app`** — the Vercel project itself was renamed at some point after the initial deploy (outside any session that touched this repo's code), confirmed live during the SelfLlama rename's verification pass: `https://ollama-configuration.vercel.app` now 307-redirects to `https://selfllama.vercel.app/`. `docs/index.html`'s canonical/OG/JSON-LD URLs and `docs/robots.txt`/`docs/sitemap.xml` were updated to the real domain in that same pass. `docs/screenshots/` holds the images it embeds (GUI detection/model steps, launcher).

### Download section

The `#download` section (and the hero's "Télécharger les apps de bureau" button, which anchors there instead of linking out to the generic Releases page) renders one card per app (`gui`/`launcher`), each with a Linux row (`.deb`/`.rpm`/`.AppImage`) and a Windows row (`.msi`/`.exe`). A small inline `<script>` fetches `api.github.com/repos/.../releases/latest` client-side and matches each asset by `name.startsWith('selfllama-gui-'|'selfllama-launcher-')` (`build-desktop.yml`'s `releaseAssetNamePattern`, see the Releases section) + file extension — deliberately **not** a hardcoded `/releases/latest/download/<exact filename>` link per format, since matching by prefix+extension is robust to the embedded version changing between releases (it now tracks the release tag, see the Releases section) without ever needing to update this file. The dynamic fetch sidesteps that entirely, at the cost of a runtime dependency on GitHub's API (only third-party network call this otherwise fully static page makes) — a failed/rate-limited fetch falls back to a plain link to the Releases page (`#dl-fallback`). This same "asset not found → render pending" fallback is also what made the Windows buttons safe to ship before `build-desktop.yml`'s Windows job had ever actually succeeded (it first did on `v1.1.0`): they rendered a disabled "bientôt" (soon) state instead of a dead link, with no code change needed once real `.msi`/`.exe` assets appeared. All outbound links on this page (nav, hero, footer, and the per-format download buttons) use `target="_blank" rel="noopener noreferrer"`; in-page anchors (`#screenshots`, `#features`, `#download`, `#install`) do not.

`docs/index.html` is entirely excluded from `ci.yml` (its `paths-ignore` covers all of `docs/**`, since the rest of that folder is static assets with nothing to do with the Bash/Rust toolchain) — but this page's inline `<script>` is now real, executable JS, not the inert JSON-LD block it had before. `.github/workflows/docs-lint.yml` closes that gap with a minimal `node --check` syntax pass, scoped specifically to `docs/index.html` (not all of `docs/**`, so a screenshot/`robots.txt`/`sitemap.xml`-only change still triggers nothing). This is deliberately syntax-only, not a full lint: there's no ESLint (or any JS lint) anywhere else in this repo either — `gui/dist`/`launcher/dist`'s own vanilla JS has no static lint step, only indirect coverage via the WebdriverIO e2e suites driving the real compiled app, which doesn't apply to a plain static page with no app behind it.

### SEO/GEO

`docs/index.html`'s `<head>` carries Open Graph and Twitter Card meta tags, a `rel="canonical"` link, and a `SoftwareApplication` JSON-LD block; `docs/robots.txt` (allow-all, pointing at the sitemap) and `docs/sitemap.xml` (single URL, the site is one page) sit alongside it; `docs/llms.txt` follows the emerging [llms.txt](https://llmstxt.org/) convention — a plain-Markdown summary of the project (what it does, the two platform implementations, model tiers, the two desktop apps) with links to the real README/releases, aimed at LLM crawlers/GEO (generative engine optimization) rather than traditional search indexing.

All of this was originally written and committed **before** the site's actual first deploy, assuming `https://ollama-configuration.vercel.app` as the domain. **Re-verified against the real deployed site in a later session**: the Vercel project was renamed to `selfllama` at some point after that initial deploy (see [Showcase site](#showcase-site-docs) above) - the old domain now 307-redirects to `https://selfllama.vercel.app/`, and every canonical/OG/JSON-LD URL in `docs/index.html` plus `docs/robots.txt`/`docs/sitemap.xml` was updated to match. That same live check also surfaced a real, currently-unresolved issue worth flagging for whoever looks at this next: the live page's `#download` section showed *"Impossible de récupérer la dernière release depuis l'API GitHub"* (its client-side `fetch` against `api.github.com/repos/.../releases/latest` failing) at the moment it was checked - not reproduced against a second fetch in the same session, so this could be a transient GitHub API rate limit (unauthenticated calls are capped at 60/hour per source IP) rather than a real regression; worth a deliberate re-check (and, if it reproduces, capturing the actual HTTP status/error body) before assuming either way. **Still not done**: a dedicated 1200×630 OG image (still reusing the 948×790 product screenshot), Search Console submission, and a real Lighthouse/Core Web Vitals check - none of these require more than the live deployment already available, just haven't been picked up yet.

## Conventions

- Every script starts with `set -euo pipefail` and `cd "$(dirname "$0")"` (Bash) or `$ErrorActionPreference = 'Stop'` (PowerShell).
- Scripts are idempotent: they check whether something is already installed/running before acting.
- All user-visible strings are in English for the Bash/PowerShell scripts (see `f174bb7`, which translated the originally-French comments/log messages). The Tauri frontends (`gui/dist/`, `launcher/dist/`) use French UI strings by design.
- Open WebUI runs as a user-level service, not system-level: `systemctl --user` on Linux, a per-user Scheduled Task on Windows. Linux autostart without an active login session needs `sudo loginctl enable-linger $USER`.
- Open WebUI is deployed with `WEBUI_AUTH=False` (no login) and, since the LAN-access toggle, listens on `127.0.0.1` only by default — see [Open WebUI LAN access toggle](#open-webui-lan-access-toggle) and [README.md's Security note](README.md#security-note). `WEBUI_AUTH` and the bind address are deliberately independent switches; don't couple them (e.g. don't make enabling LAN access also flip `WEBUI_AUTH`) without asking first, since that's a product decision, not a bug fix.
- The `AMD_GFX_OVERRIDE` map in `02-configure-gpu.sh` must be updated when ROCm adds official support for a GFX generation (remove the entry) or when a new unsupported generation ships (add the entry).
- Commit messages must follow Conventional Commits (see [Releases](#releases) above) — enforced by a husky/commitlint hook once `npm install` has been run at the repo root.
- The two `# shellcheck disable=` directives in `03-pull-models.sh` (file-wide `SC2034` for the nameref-only-read `MODEL_*`/`CAND_*` arrays, and a line-level `SC2004` on `tier_models[$usage]=`) are deliberate, verified false positives, not lint debt — see the comments right above each for why. Don't "fix" the `SC2004` one by dropping the `$`: `tier_models` is a nameref to an associative array, and doing so silently writes to a literal `usage` key instead of the intended tier/usage (verified in bash: `arr[key]=` and `arr[$key]=` are different keys for associative arrays, unlike indexed ones).
- `dialog`/`whiptail` are optional, never auto-installed: `02-configure-gpu.sh` and `03-pull-models.sh` use them when present and the terminal is interactive, and silently fall back to plain `read`/default-model behavior otherwise (or always, with `--no-tui`). Windows has no TUI equivalent.
